TensorFlow, Keras & PyTorch
The framework war is effectively over — PyTorch won research and most of industry, and TensorFlow kept the deployment ecosystem. So nobody is really testing which you prefer. What the question is testing is whether you have actually trained models, and that shows up in four bugs: gradients that accumulate because you forgot to zero them, dropout left on at inference, a loss that returns infinity because the sigmoid saturated, and a validation loop quietly building a graph it will never use. None of the four raises an error. All four are checkable arithmetic, worked below.

The row that used to decide everything — dynamic versus static graphs — has largely collapsed. TensorFlow 2 made eager execution the default and PyTorch 2 added torch.compile, so both now offer the same bargain: write and debug eagerly, then compile the hot path. The remaining differences are ecosystem rather than capability, and the honest summary is that your model's weights are the asset and the framework is a detail — ONNX exists precisely so that choice need not be permanent.
Where the choice still bites is deployment target. If the answer has to run in a browser, on Android, or on a microcontroller, TensorFlow's Lite and JS paths remain the most mature and that alone can settle it. If you are fine-tuning anything from the Hugging Face ecosystem, the decision was made for you. And on TPUs, JAX and TensorFlow are the supported route.

TensorFlow 2.x — Core Patterns
🐍 Python
import tensorflow as tf
from tensorflow import keras

# ─── 1. SEQUENTIAL API (simple) ───────────────────────────────
model = keras.Sequential([
    keras.layers.Input(shape=(20,)),
    keras.layers.Dense(64, activation='relu'),
    keras.layers.BatchNormalization(),
    keras.layers.Dropout(0.3),
    keras.layers.Dense(32, activation='relu'),
    keras.layers.Dense(1, activation='sigmoid')
])

# ─── 2. FUNCTIONAL API (for complex graphs) ───────────────────
inputs = keras.Input(shape=(20,))
x = keras.layers.Dense(64, activation='relu')(inputs)
x = keras.layers.BatchNormalization()(x)
x = keras.layers.Dropout(0.3)(x)
outputs = keras.layers.Dense(1, activation='sigmoid')(x)
model = keras.Model(inputs, outputs)

# ─── 3. COMPILE + TRAIN ───────────────────────────────────────
model.compile(
    optimizer=keras.optimizers.AdamW(learning_rate=1e-3, weight_decay=1e-4),
    loss='binary_crossentropy',
    metrics=['AUC', 'Precision', 'Recall']
)

callbacks = [
    keras.callbacks.EarlyStopping(patience=5, restore_best_weights=True),
    keras.callbacks.ReduceLROnPlateau(factor=0.5, patience=3),
    keras.callbacks.ModelCheckpoint('best_model.keras', save_best_only=True)
]

history = model.fit(
    X_train, y_train,
    validation_split=0.2,
    epochs=100,
    batch_size=64,
    callbacks=callbacks
)

# ─── 4. SUBCLASSED MODEL (custom training loop) ───────────────
class CustomModel(keras.Model):
    def __init__(self):
        super().__init__()
        self.dense1 = keras.layers.Dense(64, activation='relu')
        self.out = keras.layers.Dense(1, activation='sigmoid')
    def call(self, x, training=False):
        return self.out(self.dense1(x))
    def train_step(self, data):
        X, y = data
        with tf.GradientTape() as tape:
            y_pred = self(X, training=True)
            loss = self.compute_loss(y=y, y_pred=y_pred)
        grads = tape.gradient(loss, self.trainable_variables)
        self.optimizer.apply_gradients(zip(grads, self.trainable_variables))
        return {m.name: m.result() for m in self.metrics}

# ─── 5. SAVE / EXPORT ─────────────────────────────────────────
model.save('model.keras')                   # Keras format
model.export('saved_model/')                # TF SavedModel for serving
# TFLite for mobile:
converter = tf.lite.TFLiteConverter.from_keras_model(model)
tflite_model = converter.convert()
The shape of the two code blocks is the real difference. Keras hands you a training loop and asks you to configure it through compile and callbacks; PyTorch hands you the pieces and asks you to write the loop. That is why Keras is faster to a working baseline and PyTorch is easier to modify when the thing you need — a custom gradient step, an unusual schedule, two optimisers — is not something the loop anticipated. Neither is better; they fail in opposite directions, and train_step in the subclassed model above is Keras's escape hatch back towards the PyTorch position.

Key Differences Deep Dive
  • Computational graph: PyTorch builds graph dynamically as you execute (eager by default). TF 2 is also eager but @tf.function compiles to static graph for speed — can be hard to debug.
  • Debugging: PyTorch = put a print() or breakpoint anywhere. TF graph mode = must use tf.print() inside the graph.
  • GPU memory: TF claims all GPU memory upfront; set tf.config.experimental.set_memory_growth(gpu, True) to avoid this.
  • DDP training: PyTorch DistributedDataParallel is cleaner API than TF's MirroredStrategy for multi-GPU.
The debugging row has a specific trap worth stating precisely: inside a compiled function, ordinary Python statements run only during tracing, not on every call. So a print() in a @tf.function fires once and then never again, and a Python counter incremented there stops incrementing — which reads as the code not running when it is running fine. That is also why compiled functions want tensor operations rather than Python side effects, and why the practical rule is to debug eagerly and compile afterwards.
Common Gotchas
  • PyTorch: forget zero_grad() → accumulated gradients. Forget model.eval() → dropout active during inference.
  • TF/Keras: training=True/False controls BN and Dropout — pass it in model(x, training=True). Default model.predict() sets training=False.
  • Data shapes: PyTorch expects [B, C, H, W] (NCHW); TF expects [B, H, W, C] (NHWC) — a common transposition bug.
  • Loss functions: PyTorch BCEWithLogitsLoss (logits) ≠ BCELoss (probs). Use the logits version — numerically stable.
On the shapes row: a layout mismatch usually does raise a shape error, which is the good case. The dangerous case is when the dimensions happen to be compatible — a square image where height equals width, or a batch that coincidentally matches the channel count — so the tensor flows through and trains on transposed data. Assert the expected shape at the boundary of your data loader rather than relying on a downstream layer to complain.
Worked — the four silent bugs, as arithmetic
None of these raises an exception, which is exactly why they survive. All four are arithmetic you can check.
1. Gradients accumulate. PyTorch adds each backward() into .grad rather than replacing it, because that is what makes gradient accumulation across micro-batches possible. Omit zero_grad() and the gradient at step k is the sum of all k batches:
backward() calls without zero_grad()1234
Gradient norm (single-batch norm = 1.005)1.0052.0103.0154.020
The optimiser then takes a step k times too large, so the symptom is a loss that oscillates or diverges after a few iterations while the code looks correct — and it is easily misdiagnosed as a learning rate that needs lowering, which partially masks it and wastes a day.
2. BCELoss overflows where BCEWithLogitsLoss does not — and sooner than people expect. In float32, sigmoid(z) rounds to exactly 1.0 at z ≈ 17, a logit a confident model reaches routinely. Then log(1 − p) is log(0):
logit zfloat32 sigmoid(z)1 − pBCELoss (target 0)BCEWithLogitsLoss
160.99999991.19e-0715.9416.00
171.00.0inf17.00

The row above the cliff is already wrong. At z = 16 the naive form returns 15.94 where the true loss is 16.00 — the error arrives before the overflow does, because 1 − p has already lost most of its significant digits. The stable version never forms 1 − p at all: it computes log(1 + e^z) directly via log-sum-exp, which is why it stays correct on both rows. An inf loss produces nan gradients, and once a weight is nan it stays nan forever — the model does not degrade, it dies, and the traceback points nowhere. Pass logits, not probabilities, and let the loss apply the sigmoid.
3. model.eval() is not cosmetic. It changes two layers. Dropout stops zeroing activations, and BatchNorm switches from batch statistics to its running estimates. Leave it in training mode at inference and the same input returns a different answer on every call — and worse, BatchNorm normalises using the statistics of whatever happened to be in the batch, so a prediction depends on the other rows you scored alongside it. With batch size 1 the batch variance is zero and the output is meaningless. This is the bug where offline evaluation looks fine (large batches) and single-request serving is wrong.
4. torch.no_grad() is about memory, not correctness. Without it a validation pass still records the graph for a backward that never comes, so activations are retained for every layer and every batch. The result is a validation loop that OOMs on a model that trained fine — confusing, because validation is the cheaper operation. torch.inference_mode() goes slightly further and is the modern default.
Mistakes that survive code review
  • Missing optimizer.zero_grad(). Gradients are summed, so after k batches the step is k times too large. Loss oscillates, nothing errors, and lowering the learning rate half-hides it
  • BCELoss on sigmoid output instead of BCEWithLogitsLoss on logits. float32 sigmoid saturates at a logit of about 17, giving log(0) → inf → nan weights that never recover
  • Missing model.eval() at inference. Dropout stays active and BatchNorm uses batch statistics, so a prediction depends on what else was in the batch — and is meaningless at batch size 1
  • Forgetting model.train() again after validation. The mirror-image bug: training continues with dropout disabled and BatchNorm frozen, and the model quietly overfits
  • Validation without torch.no_grad(). Builds a graph for a backward pass that never happens; the symptom is an OOM in the cheap half of the loop
  • Python side effects inside @tf.function. They run during tracing only, so a print() fires once and a counter stops counting. Debug eagerly, compile after
  • NCHW/NHWC mismatches passed through on compatible dimensions. Usually a shape error, occasionally silent when height equals width. Assert shapes at the data-loader boundary
  • Letting TensorFlow claim the whole GPU. It allocates all memory on init, so a second process on the same card fails. Set memory growth
  • Comparing frameworks on speed rather than ecosystem. Both compile to similar kernels; what differs is the deployment target and the model zoo you need
  • Saving the whole model object rather than state_dict(). Pickling the object couples the checkpoint to your class definitions and import paths, so a refactor makes old checkpoints unloadable
  • Calling model.predict() in PyTorch. It does not exist — that is Keras and sklearn. It is model.eval() then a call inside no_grad()

🎯 In an interview

Do not take the bait on "which is better". "PyTorch for anything touching Hugging Face or needing research flexibility; TensorFlow when the deployment target is mobile, browser or TPU, where Lite and JS are still the most mature paths. But the dynamic-versus-static distinction that used to decide this has collapsed — TF 2 is eager by default and PyTorch 2 has torch.compile, so both give you the same bargain: debug eagerly, compile the hot loop. The weights are the asset; ONNX means the choice isn't permanent."

Name the four silent bugs, with the mechanism. "zero_grad() every batch, because PyTorch sums gradients — that's what makes accumulation across micro-batches possible, and it means forgetting it makes your step k times too large after k batches. model.eval() at inference, because BatchNorm otherwise uses batch statistics, so a prediction depends on what else is in the batch and is meaningless at batch size 1. BCEWithLogitsLoss over BCELoss. And no_grad() in validation, which is a memory issue rather than a correctness one."

If they push on numerical stability, have the number. "In float32 the sigmoid saturates to exactly 1.0 at a logit around 17 — not some extreme value, a routine one for a confident model. Then log(1 − p) is log(0) and the loss is inf, which makes the gradients nan, and a nan weight never recovers. BCEWithLogitsLoss computes log(1 + e^z) directly and never forms 1 − p."

On torch.compile: "It traces the graph and compiles fused kernels through TorchInductor — fusing elementwise chains into single kernels and removing Python overhead from the loop, commonly 30–50% on transformer training for one line of code. The trade is a compilation pause on the first batch and recompilation whenever shapes change, so it rewards fixed shapes and padded batches."

What not to say. Never say model.predict() in PyTorch — it does not exist and it signals you have not written a training loop. Do not argue one framework is faster; they compile to similar kernels and the difference that matters is ecosystem. Do not claim no_grad() is only for inference — validation needs it too, for memory. And do not describe the eval/train switch as a formality: it changes what BatchNorm and Dropout compute, which is a correctness issue and not a tidiness one.

Eager vs compiled execution
In code
Two of the four bugs are framework-independent arithmetic, so they can be reproduced without a GPU or a training run — which is also the clearest way to see why they are silent.
import numpy as np

# ---- 1. WHY zero_grad() EXISTS ------------------------------------------
# PyTorch ADDS each backward() into .grad rather than replacing it (that is
# what makes gradient accumulation over micro-batches possible). Omit
# zero_grad() and the step at iteration k uses the SUM of k batches.
per_batch_grad = np.array([0.4, -0.2, 0.9])
acc = np.zeros(3)
for k in range(1, 5):
    acc = acc + per_batch_grad                 # no zero_grad()
    print(f"  after {k} backward(): grad={acc.round(2)}  norm={np.linalg.norm(acc):.3f}")
# norm grows 1.005, 2.010, 3.015, 4.020 -- the optimiser steps k times too far.
# Symptom: loss oscillates or diverges. No exception is ever raised.

# ---- 2. WHY BCEWithLogitsLoss EXISTS ------------------------------------
# In float32 the sigmoid saturates to EXACTLY 1.0 at a logit of about 17 --
# a value a confident model reaches routinely, not an extreme one.
print(f"\n{'logit':>6} {'sigmoid':>12} {'1-p':>12} {'BCELoss':>10} {'BCEWithLogits':>14}")
for z in (16.0, 17.0, 30.0):
    z32 = np.float32(z)
    p   = np.float32(1.0 / (1.0 + np.exp(-z32)))          # sigmoid, then BCELoss
    with np.errstate(divide='ignore'):
        naive = -np.log(np.float32(1.0) - p)              # target = 0
    stable = np.float32(np.logaddexp(0.0, z32))           # log(1 + e^z)
    print(f"{z:6.0f} {p:12.7f} {np.float32(1.0)-p:12.3e} {naive:10.2f} {stable:14.2f}")
# At z=17: 1-p underflows to 0, so log(0) = -inf -> loss inf -> nan gradients,
# and a nan weight never recovers. The stable form never forms (1 - p).

# ---- 3. THE TWO MODE BUGS, stated precisely -----------------------------
# model.eval()  : dropout off, BatchNorm uses RUNNING stats. Without it a
#                 prediction depends on the other rows in the batch, and is
#                 meaningless at batch size 1.
# torch.no_grad(): a memory fix, not a correctness one -- otherwise validation
#                 retains activations for a backward pass that never happens.
