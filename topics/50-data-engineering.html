Data Engineering for ML
The two failures that kill more production models than any modelling mistake are training–serving skew and point-in-time leakage, and they are the same bug wearing different clothes: the offline job can see the future and across the whole dataset, while the live service sees one row at one instant. Almost everything here — feature stores, as-of joins, table formats with time travel, idempotent partitioned writes — exists to make the offline world obey the constraints the online world cannot escape. Get that right and the modelling is the easy part; get it wrong and you ship a model with a beautiful offline score and no production value.
Why Data Engineering Is an ML Bottleneck
  • Data scientists spend 80% of time on data — finding, cleaning, transforming, validating — and only 20% on modelling
  • Training-serving skew: features computed differently in training pipelines vs inference APIs causes silent model degradation — the most common production ML failure
  • Reproducibility: without versioned data and deterministic pipelines, experiments can't be reproduced and bugs can't be traced
  • Scale: pandas works for millions of rows; real training data is often hundreds of billions of rows requiring distributed compute
The word doing the work in the second bullet is silent. A skewed feature does not raise an exception, fail a test, or show up in the model's logs — it produces a confident prediction from a distribution the model never trained on. There is no stack trace, so the failure surfaces weeks later as an unexplained drop in a business metric, which is why the engineering answer is structural (one definition, used by both paths) rather than diligence.

Do not build all seven layers before the first model ships. A single scheduled job writing partitioned parquet, with a schema assertion at the top, will carry a team a long way — and the layers earn their place one incident at a time. The layer to add first is whichever one your last outage came from, and the one teams most often add too late is data quality, because it is the only one that turns a silent corruption into a loud failure.
Part 1 — Apache Spark for ML Data Pipelines
Spark — and the three numbers that decide whether a job finishes
Spark is the dominant framework for processing data too large for pandas. It distributes computation across a cluster, processes data in-memory (vs Hadoop MapReduce's disk-based approach), and provides DataFrame, SQL, and ML APIs.
from pyspark.sql import SparkSession
from pyspark.sql import functions as F
from pyspark.sql.window import Window

spark = SparkSession.builder \
    .appName("MLFeaturePipeline") \
    .config("spark.sql.adaptive.enabled", "true") \
    .getOrCreate()

# Read 100M+ row parquet from S3
df = spark.read.parquet("s3://bucket/transactions/")

# Compute rolling 30-day payment rate per customer
w = Window.partitionBy("customer_id") \
          .orderBy("txn_date") \
          .rangeBetween(-30*86400, 0)  # 30 days in seconds

df_features = df.withColumn(
    "paid_30d", F.sum("is_paid").over(w)
).withColumn(
    "txns_30d", F.count("*").over(w)
).withColumn(
    "payment_rate_30d",
    F.col("paid_30d") / F.col("txns_30d")
)

# Write training dataset to Delta Lake
df_features.write \
    .format("delta") \
    .mode("overwrite") \
    .save("s3://bucket/features/payment_rate/")
Key Spark concepts for ML
  • Lazy evaluation: transformations are not executed until an action (write, collect, show). Spark builds a DAG of operations and optimises before running
  • Partitioning: data is split into partitions processed in parallel. Key for performance — too few = underutilised, too many = scheduling overhead. Rule: 128MB–1GB per partition
  • Window functions: rolling aggregations (7d/30d/90d rates) are core ML features; Spark window functions are the scalable alternative to pandas groupby + rolling
  • Adaptive Query Execution (AQE): auto-optimises join strategies and partition sizes at runtime — always enable in Spark 3+
  • Broadcast join: when one table is small (<10MB), broadcast it to all workers to avoid expensive shuffle join
Those bullets become actionable once you put numbers through them, and in practice three numbers explain most slow Spark jobs.

The default of 200 shuffle partitions is the single most common performance bug, because it is a fixed number applied to data of any size: harmless on 20 GB, fatal on 1 TB. And note why skew is worse than it looks — Spark's stage boundary is a barrier, so every other executor sits idle waiting for the straggler. You are not paying 20× on one task; you are paying for the whole cluster to wait.
Common Spark performance pitfalls

Data skew: one partition has 10× more data than others → one task takes 10× longer, blocking the job. Fix: salting keys, skew hints, or AQE skew join. Shuffle: groupBy + join operations require shuffling data across the network — the most expensive operation. Minimise shuffles; cache intermediate results if reused. UDFs: Python UDFs break Spark's JVM optimisations. Use built-in SQL functions (F.*) wherever possible.

On that last point, the reason is worth knowing rather than memorising: a Python UDF forces every row out of the JVM, through a serialisation boundary into a Python process, and back. Catalyst cannot see inside it, so predicate pushdown and whole-stage codegen both stop at the UDF. Pandas/Arrow UDFs move data in vectorised batches instead of row by row and recover most of the gap — but a built-in F.* expression stays in the JVM and remains the right default.
Part 2 — dbt for ML Feature Engineering
dbt — Data Build Tool
dbt transforms raw data in your data warehouse using SQL SELECT statements. It handles dependency ordering, incremental loading, testing, and documentation — everything you'd write boilerplate Python for, dbt handles declaratively.
-- models/features/customer_payment_rate.sql
-- dbt model: computes 30-day payment rate per customer

{{
  config(
    materialized = 'incremental',
    unique_key   = ['customer_id', 'snapshot_date'],
    partition_by = {'field': 'snapshot_date', 'data_type': 'date'}
  )
}}

with base as (
    select
        customer_id,
        snapshot_date,
        count(*) as txns_30d,
        sum(case when status='paid' then 1 else 0 end)
            as paid_30d
    from {{ ref('stg_transactions') }}  -- refs ensure ordering
    where txn_date between
        dateadd('day', -30, snapshot_date) and snapshot_date
    {% if is_incremental() %}
        and snapshot_date > (select max(snapshot_date) from {{ this }})
    {% endif %}
    group by 1, 2
)

select
    customer_id,
    snapshot_date,
    paid_30d / nullif(txns_30d, 0) as payment_rate_30d,
    txns_30d
from base
Why dbt for ML
  • Version-controlled SQL: feature logic is in git — auditable, reviewable, reproducible
  • DAG of dependencies: dbt resolves ref() calls into the correct build order automatically
  • Incremental models: only process new data; don't recompute the whole history on every run — essential for large feature tables
  • Built-in testing: not_null, unique, accepted_values, relationships tests validate every model run
  • dbt docs: auto-generated data lineage graph and data dictionary — "what does this feature mean and where does it come from?"
dbt vs Spark for ML

Use dbt when your data is already in a warehouse (BigQuery, Snowflake, Redshift) and fits in SQL. Use Spark when data lives in a data lake (S3/GCS), is very large (>1TB), requires complex windowed aggregations, or needs Python/MLlib transformations. Most modern stacks use both: Spark for raw ingest + heavy processing, dbt for curated feature engineering inside the warehouse.

Why incremental models are not an optimisation but a requirement. A daily customer snapshot table over 10M customers and three years of history is 10.95 billion rows. Rebuilding it every night processes all of that to add one day; an incremental run processes 10 million — about 1,095× less work. The tell that a team has not made this jump is a nightly job whose runtime grows linearly with the age of the product.
The catch, and it is the part that bites: an incremental model is only correct if late-arriving data cannot change already-built partitions. A payment that settles three days after the transaction date silently invalidates a snapshot you already wrote. The standard answer is a bounded lookback — rebuild the trailing N days on every run rather than only the newest one — and a periodic full refresh to repair drift. Choose N from the actual lateness distribution of the source, not from a round number.
Two more things dbt gives ML teams that are easy to undervalue. Tests run on every build, so a broken data contract fails the pipeline rather than the model — and a `not_null` on a feature column is worth more than most monitoring. And ref() produces the lineage graph, which is what turns "this feature looks wrong" into "these four models consume it and here is where it came from".
# dbt tests in schema.yml — run automatically after every build
models:
  - name: customer_payment_rate
    columns:
      - name: customer_id
        tests:
          - not_null
          - unique  # each customer appears once per snapshot date
      - name: payment_rate_30d
        tests:
          - not_null
          - dbt_utils.accepted_range:
              min_value: 0
              max_value: 1  # rate must be in [0,1]
Part 3 — Table Formats: Delta Lake & Apache Iceberg
Why Table Formats Matter for ML
Raw parquet files in S3 are immutable and stateless — you can't update a row, roll back, or read consistent snapshots. Delta Lake and Iceberg add ACID transactions, versioning, and time travel on top of parquet, solving critical ML data engineering problems.
The concrete failure that motivates all of this: a directory of parquet files has no commit point. A job halfway through writing 500 files has published 250 of them, and a training job reading that path gets a dataset that is not any version of the truth — not the old one, not the new one. Nothing errors. You train on it. A table format adds an atomic metadata pointer, so readers see the old snapshot until the new one is complete, which is the whole difference between a directory and a table.
Delta Lake (Databricks)
  • ACID transactions: concurrent reads and writes without corruption; no more partial writes breaking downstream jobs
  • Time travel: query any historical version — VERSION AS OF 42 or TIMESTAMP AS OF '2024-01-01'
  • Schema enforcement + evolution: rejects writes that don't match the schema; controlled schema changes
  • DML operations: UPDATE, DELETE, MERGE INTO — update individual rows in parquet (previously impossible)
  • Z-order clustering: co-locate related data on disk for faster queries on common filter columns
from delta.tables import DeltaTable

# Time travel: reproduce training dataset from 3 months ago
df_train = spark.read.format("delta") \
    .option("timestampAsOf", "2024-01-15") \
    .load("s3://bucket/features/payment_rate/")

# Upsert (MERGE): update existing rows, insert new ones
DeltaTable.forPath(spark, "s3://bucket/features/") \
    .alias("target") \
    .merge(new_data.alias("source"),
           "target.customer_id = source.customer_id") \
    .whenMatchedUpdateAll() \
    .whenNotMatchedInsertAll() \
    .execute()
Apache Iceberg (Netflix / Apple)
  • Same core features as Delta Lake: ACID, time travel, schema evolution
  • Hidden partitioning: partitions managed by Iceberg, not exposed to query writers — no need to remember WHERE dt=...
  • Multi-engine support: natively supported by Spark, Flink, Trino, Hive, DuckDB — Delta is more tightly coupled to Spark/Databricks
  • Partition evolution: change partition strategy on existing data without rewriting
  • Row-level deletes: GDPR deletion (right to erasure) without rewriting entire partitions
Delta vs Iceberg

Delta Lake is the default if you're on Databricks or already use Spark heavily. Iceberg is preferred for multi-engine environments (Flink + Spark + Trino) or when hidden partitioning is important. Both are production-ready; the choice is often ecosystem fit rather than capability gap.

For ML specifically, time travel is the feature that pays for the migration. "Reproduce the exact training set from six months ago" turns from an archaeology project into one clause in a query — which is what makes a model debuggable at all. Two caveats: retention is finite, so a VACUUM that reclaims storage also destroys the versions you were relying on (set retention against your model audit window, not the default), and time travel versions the table, not your feature logic — pin the code version alongside it or you can reproduce the data and not the dataset.
Part 4 — Feature Pipelines: Batch vs Streaming
Batch Feature Pipelines
Compute features on a schedule (hourly, daily, weekly) from historical data. Best for features that don't need sub-minute freshness and where history matters.
Typical Airflow DAG pattern 
from airflow import DAG
from airflow.providers.apache.spark.operators.spark_submit import SparkSubmitOperator
from airflow.providers.dbt.cloud.operators.dbt import DbtCloudRunJobOperator

with DAG("ml_feature_pipeline",
         schedule_interval="0 3 * * *",  # 3am daily
         catchup=False) as dag:

    # Step 1: Run Spark job to compute raw aggregations
    spark_agg = SparkSubmitOperator(
        task_id="compute_raw_features",
        application="s3://code/feature_agg.py",
        conf={"spark.executor.memory": "8g"}
    )

    # Step 2: dbt transformation inside warehouse
    dbt_features = DbtCloudRunJobOperator(
        task_id="dbt_feature_models",
        job_id=12345
    )

    # Step 3: Materialise to feature store
    load_feast = PythonOperator(
        task_id="load_to_feature_store",
        python_callable=push_to_feast
    )

    spark_agg >> dbt_features >> load_feast
Make every task idempotent. A rerun of yesterday must replace yesterday, not append to it — which means writing to a partition keyed by the logical date and overwriting that partition, never appending to a single growing table. Retries are automatic and backfills are routine, so a non-idempotent task does not fail loudly; it silently double-counts, and a duplicated event inflates every count feature computed from it.
Point-in-time correct joins — the critical concept
  • When building training data, you must use feature values that were available at the time of the label event — not current values
  • Example: predicting default on a loan application filed Jan 15. The customer's 30-day payment rate feature must be computed as of Jan 15 — not today's value (which might reflect the loan outcome)
  • Using future feature values = target leakage — model looks great in training but fails in production
  • Feature stores (Feast, Tecton) implement point-in-time joins automatically
# Feast point-in-time correct retrieval
training_df = store.get_historical_features(
    entity_df=loan_applications_df,  # has event_timestamp
    features=[
        "customer_features:payment_rate_30d",
        "customer_features:income_to_debt_ratio",
    ]
).to_df()
# Feast joins features as of each row's event_timestamp
# — no future leakage
worked — the join that leaks, in three rows

The code card at the end of this topic runs it. User 1 has credit scores of 610 from January, 655 from April, and 700 from June; their label event is dated 1 March. A groupby(user).last() join — the natural thing to write, and the most common form of this bug — attaches 700, a June fact, to a March label. The as-of join with direction='backward' attaches 610, the only value that existed on the day. The offline model trained on the first version knows the future; the live service, which can only read today's value at today's timestamp, does not. That is training–serving skew and target leakage arriving through the same line of code.

Two details that decide whether an as-of join is actually correct. Use the timestamp at which a fact became available to your systems, not the timestamp it describes — a credit score dated 1 March but ingested on 5 March was not knowable on the 3rd, and the gap between event time and ingest time is where leakage hides after you have fixed the obvious version. And define the boundary: if a feature is stamped at exactly the label instant, decide deliberately whether it is admissible, because < and <= differ by exactly the events you most want to exclude.
Streaming Feature Pipelines — Kafka + Flink
For features that must be fresh within seconds — fraud detection velocity signals, real-time session features, live inventory counts. Streaming pipelines consume events as they arrive and maintain continuously updated aggregations.
from pyflink.datastream import StreamExecutionEnvironment
from pyflink.table import StreamTableEnvironment

env = StreamExecutionEnvironment.get_execution_environment()
t_env = StreamTableEnvironment.create(env)

# Consume from Kafka topic
t_env.execute_sql("""
    CREATE TABLE transactions (
        customer_id BIGINT,
        amount      DOUBLE,
        is_fraud    BOOLEAN,
        event_time  TIMESTAMP(3),
        WATERMARK FOR event_time AS event_time - INTERVAL '5' SECOND
    ) WITH (
        'connector' = 'kafka',
        'topic'     = 'transactions',
        'format'    = 'json'
    )
""")

# Sliding window: count transactions in last 1 hour
t_env.execute_sql("""
    CREATE TABLE velocity_features AS
    SELECT
        customer_id,
        COUNT(*) AS txn_count_1h,
        SUM(amount) AS txn_amount_1h,
        TUMBLE_START(event_time, INTERVAL '1' HOUR) AS window_start
    FROM transactions
    GROUP BY customer_id,
             TUMBLE(event_time, INTERVAL '1' HOUR)
""")
Streaming architecture for ML
  • Kafka: event bus — all raw events (transactions, clicks, logins) published as topics; durable, replayable
  • Flink: stateful stream processor — maintains running aggregations (counts, sums, rates) in memory as events arrive; checkpoints to S3/HDFS for fault tolerance
  • Redis: online feature store — Flink writes computed features to Redis; model inference API reads from Redis in <1ms
  • Lambda architecture: batch pipeline (daily) for accuracy on historical features; streaming pipeline (real-time) for freshness on velocity features — results merged at serving time
Stream only what freshness actually requires. A card-testing attack runs its course in minutes, so a velocity count that is 24 hours stale is worth nothing — that feature must stream. A 90-day average balance changes imperceptibly overnight and streaming it buys nothing for real cost. Sort features by how fast the signal decays, and let the slow majority stay in the cheap, easily-backfilled batch path.
The concept that makes streaming features correct is the watermark, which is the pipeline's explicit statement about lateness: the INTERVAL '5' SECOND in the SQL above declares that events more than five seconds late will be dropped rather than waited for. That is a deliberate accuracy-for-latency trade, and the number belongs to the domain, not the framework. Note the consequence for ML — a windowed aggregate can be slightly different when recomputed later, because the stream saw a different set of events than the batch backfill does. If the same feature is produced by both paths, they will disagree at the margins, and reconciling them (or declaring one authoritative for training) is the real work in a lambda architecture.

Join fanout deserves its own alarm. It is the only row here that inflates your metrics rather than degrading them: duplicated rows make counts larger, models more confident, and offline scores better. Assert the row count is unchanged after every join that should be many-to-one — one line, and it catches the class of bug that otherwise gets discovered by a suspicious improvement.
import great_expectations as gx

# Define data contract as expectations
context = gx.get_context()
suite = context.add_expectation_suite("feature_suite")

# Add expectations
validator.expect_column_values_to_not_be_null(
    "payment_rate_30d"
)
validator.expect_column_values_to_be_between(
    "payment_rate_30d", min_value=0, max_value=1
)
validator.expect_column_values_to_be_unique(
    "customer_id"  # one row per customer
)
validator.expect_table_row_count_to_be_between(
    min_value=1_000_000,  # should have at least 1M rows
    max_value=10_000_000
)

# Run validation before model training
results = validator.validate()
if not results.success:
    raise ValueError("Data quality check failed — abort training")
The gate matters more than the expectations. A quality suite that logs a warning and lets the pipeline continue is a report nobody reads; the same suite raising and aborting the training run is a control. Fail the build, and make the failure page whoever owns the upstream table — data quality without an owner degrades to a dashboard.
Distinguish the two kinds of check, because they need different responses. Contracts are absolute — a rate outside [0,1], a null in a required key, a missing column — and they should hard-fail immediately. Distribution checks are relative, and a PSI alarm may be a genuine population change rather than a bug, so it should page a human rather than block the pipeline. Wiring drift alerts to hard failures is how teams end up ignoring both.
Mistakes that survive code review
  • Latest-value joins in training data. groupby(user).last() attaches a fact from after the label event. It is one line, it looks like normal pandas, and it is the most common leak in ML — use an as-of join with an explicit backward direction
  • Joining on event time instead of availability time. A fact dated 1 March but ingested on the 5th was not knowable on the 3rd. Fixing the obvious leak and leaving this one is the usual second act
  • Two implementations of one feature. Spark SQL for training, Python for serving. They diverge on the cases nobody wrote a test for — a left join giving NULL where the service gives 0.0 — and the model degrades silently. One definition, both paths
  • Non-idempotent pipeline tasks. Retries and backfills are routine, so an append-based task double-counts on rerun and inflates every count feature downstream. Write to a date partition and overwrite it
  • Overwriting a parquet directory instead of committing a table. There is no atomic point, so a reader mid-write gets a dataset that is not any version of the truth. Use Delta or Iceberg and MERGE
  • Leaving spark.sql.shuffle.partitions at 200. Fine at 20 GB, 5.12 GB per partition at 1 TB. It is a fixed number applied to data of any size
  • Ignoring skew because the average partition looks fine. One key with 10% of the rows is 20× the average task, and the whole cluster waits at the stage barrier
  • Incremental models with no lookback for late data. A payment settling three days late silently invalidates a partition you already wrote. Rebuild a trailing window sized from the real lateness distribution
  • Streaming features that did not need streaming. A 90-day average does not change overnight. Stream what decays fast; batch the rest, where backfilling is cheap
  • Quality checks that warn instead of failing. If a validation cannot stop the training run, it is documentation
  • VACUUM with default retention on a table you rely on for reproducibility. Reclaiming storage also deletes the versions your audit window assumes. And time travel versions the table, not your transformation code — pin both
  • Using pandas for 100M+ rows. It loads everything into RAM. Spark, DuckDB or Polars — and DuckDB in particular now covers a lot of what used to require a cluster

🎯 In an interview

Frame the whole area as a problem about time. "The two failures that kill production models — training–serving skew and point-in-time leakage — are the same bug: the offline job can see the future and the whole dataset, the online service sees one row at one instant. Feature stores, as-of joins and time-travelling table formats all exist to force the offline world to obey the online world's constraints."

Explain point-in-time correctness with the three-row example, not the definition. "If a user's credit score was 610 in January, 655 in April and 700 in June, and the label event is 1 March, then a latest-value join attaches 700 — a June fact on a March label. The as-of join attaches 610, the only value that existed. Then the detail that shows you have debugged this for real: join on when the fact became available, not when it happened. A score dated 1 March but ingested on the 5th still leaks."

Make training–serving skew concrete. "Training computes a 30-day payment rate in Spark with a left join, so customers with no payments get NULL. The serving API computes it in Python with an inner join and returns 0.0. The model sees a distribution it never trained on, nothing raises an exception, and the metric drifts. That is why a feature store's real value is a single definition used by both paths — not the Redis cache."

Have Spark numbers ready, because they separate people who have run jobs from people who have read about them. "The default 200 shuffle partitions puts 5.12 GB in each partition at 1 TB when you want 128 MB to 1 GB — that is most 'Spark is slow' tickets. Skew is the other: one key with 10% of a billion rows is 20× the average task, and because a stage is a barrier the whole cluster idles waiting for it. Salt the key or let AQE handle the skew join."

What not to say. Do not present a seven-layer stack as the starting point — layers earn their place one incident at a time. Do not claim a feature store prevents leakage by itself; it prevents it only if you use its point-in-time API. Do not say "we validate the data" without saying whether the check can stop the pipeline, because a warning is documentation. And do not offer streaming as the default: stream what decays fast, batch the rest, and be ready to explain that the two paths will disagree at the window edges.

Point-in-time correctness, in one picture
In code
The two patterns that matter — idempotent partitioned writes, and point-in-time correct joins. The second is where most training/serving skew is born.
import pandas as pd

# 1. IDEMPOTENT WRITES. A rerun of yesterday must REPLACE yesterday, not append
#    to it. Partition by date and overwrite the partition.
def write_partition(df, root, dt):
    df.to_parquet(f"{root}/dt={dt}/part.parquet", index=False)   # overwrite, not append

# 2. POINT-IN-TIME CORRECT JOIN -- the most common cause of a model that scores
#    brilliantly offline and fails in production.
labels = pd.DataFrame({'user': [1, 1, 2],
                       'event_ts': pd.to_datetime(['2026-03-01','2026-05-01','2026-04-01']),
                       'y': [0, 1, 1]})
features = pd.DataFrame({'user': [1, 1, 1, 2, 2],
                         'valid_from': pd.to_datetime(['2026-01-01','2026-04-01',
                                        '2026-06-01','2026-01-01','2026-05-01']),
                         'score': [610, 655, 700, 580, 640]})

# WRONG: latest value per user -- leaks the future into the past
wrong = labels.merge(features.sort_values('valid_from').groupby('user').last(), on='user')

# RIGHT: as-of join, backwards only
right = pd.merge_asof(labels.sort_values('event_ts'),
                      features.sort_values('valid_from'),
                      left_on='event_ts', right_on='valid_from',
                      by='user', direction='backward')
print(right[['user','event_ts','score','y']].to_string(index=False))
# user 1 at 2026-03-01 must see 610, never 700

# 3. Schema contracts fail loudly at the boundary, not silently downstream
def validate(df, spec):
    missing = set(spec) - set(df.columns)
    assert not missing, f"missing columns: {missing}"
    for c, t in spec.items():
        assert df[c].dtype == t, f"{c}: expected {t}, got {df[c].dtype}"
