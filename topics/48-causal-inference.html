Causal Inference & A/B Testing
Every other topic in this atlas answers what will happen. This one answers what would happen if I changed something, and they are different questions with different mathematics. A churn model that reads login frequency will be excellent at ranking who leaves and will tell you nothing about whether making people log in more keeps them — because it learned the correlation, and you are proposing to break it. The gap between $P(Y \mid X)$ and $P(Y \mid do(X))$ is where product decisions live, and closing it takes either randomisation or an explicit, defensible assumption about the counterfactual you never got to see.
Seeing is not doing
The distinction that organises everything below: observing that treated units do better is a statement about who got treated, while intervening is a statement about what treatment does. They coincide only when assignment was independent of everything else — which is exactly what randomisation buys and nothing else gives for free.
  • Correlation-based models break under intervention. Login frequency predicts retention because engaged users do both. Force logins and you have moved the feature without moving the thing it was proxying for, and the model's coefficient no longer applies
  • Confounding reverses signs, it does not merely weaken them. In the code card at the end of this topic the true effect is +2.0 and the naive treated-minus-control comparison reads −1.13. Not attenuated — the wrong sign, because the treatment went to people who were already worse off
  • Feedback loops make yesterday's data a function of yesterday's model. Predictions change behaviour, behaviour becomes training data, and the correlation you fit is partly your own reflection
  • Policy questions are always interventional. "Should we raise X?" is $do(X)$. No amount of predictive accuracy answers it
The Potential Outcomes Framework (Rubin Causal Model)
$$\begin{aligned} Y_i(1) &= \text{outcome for unit } i \text{ if treated} \\ Y_i(0) &= \text{outcome for unit } i \text{ if not treated} \\ \text{ITE}_i &= Y_i(1) - Y_i(0) \quad \text{(Individual Treatment Effect — never observable)} \\ \text{ATE} &= \mathbb{E}[Y(1) - Y(0)] \quad \text{(Average Treatment Effect)} \\ \text{ATT} &= \mathbb{E}[Y(1) - Y(0) | T=1] \quad \text{(Effect on the Treated)} \end{aligned}$$
Fundamental problem of causal inference

We can never observe both $Y_i(1)$ and $Y_i(0)$ for the same unit at the same time. We observe either the treated or the control outcome — never both. All causal methods are strategies for estimating the counterfactual we cannot observe.

Read that as a missing data problem and the whole field organises itself: exactly half of the table is always blank, so every method below is a different argument for what belongs in the blanks. Randomisation says the missing half is exchangeable with the observed half. Matching says it is exchangeable conditional on covariates. DiD says the missing half would have moved parallel to the controls. The assumption is the method, and the estimator is the easy part — which is why a causal answer without its stated assumption is not an answer.
Note also which quantities are even askable. ITE is never identified for an individual, so anything claiming per-person causal effects — uplift models included — is estimating a conditional average over people who look alike, not a personal counterfactual. ATT differs from ATE whenever the treated are not representative, and for "should we have run this campaign" ATT is usually the quantity you actually want.
Part 1 — A/B Testing: The Gold Standard
Why Randomised Experiments Are the Gold Standard
Random assignment makes treatment and control identical in expectation on every covariate — including the ones you never measured and the ones you never thought of. That last clause is the whole value proposition, and it is the one thing no observational method can replicate.
A/B test statistical setup
$$\begin{aligned} H_0&: \mu_{\text{control}} = \mu_{\text{treatment}} \quad (\text{no effect}) \\ H_1&: \mu_{\text{control}} \neq \mu_{\text{treatment}} \quad (\text{two-tailed}) \\ \text{Test stat}&: t = \frac{\bar{x}_T - \bar{x}_C}{\sqrt{s^2_T/n_T + s^2_C/n_C}} \\ p\text{-value}&: P(\text{data this extreme} | H_0 \text{ true}) \\ \text{Reject } H_0&\text{ if } p < \alpha \quad (\alpha = 0.05 \text{ typical}) \end{aligned}$$
Key concepts
  • Type I error (α): false positive — reject H₀ when it's true. α = 0.05 → 5% chance of false positive
  • Type II error (β): false negative — fail to reject H₀ when it's false
  • Statistical power (1-β): probability of detecting a true effect. Target ≥ 0.80
  • Minimum Detectable Effect (MDE): smallest effect size worth detecting; drives sample size
  • Two-tailed vs one-tailed: almost always use two-tailed — you can't know in advance which direction the effect will be
A p-value is not the probability the hypothesis is true, and 1−p is not confidence in the effect. It is the probability of data this extreme if there were no effect at all. Getting this backwards is what makes people treat p = 0.04 as "96% sure" and then ship a flat feature.
Power analysis — and what it costs to detect something smaller
$$n \approx \frac{2(z_{\alpha/2} + z_\beta)^2 \sigma^2}{\delta^2}$$
where $\delta$ = MDE (minimum detectable effect), $\sigma^2$ = variance of metric, $z_{\alpha/2}$ = 1.96 for α=0.05, $z_\beta$ = 0.84 for 80% power.
The term that dominates is $\delta^2$ in the denominator, and it is worth seeing what that means in traffic. From a 10% baseline conversion rate, at 80% power and α = 0.05:
MDEn per groupTotal usersAt 5,000 users/day

Halving the MDE multiplies the sample by about four (3.85× in the rows above — not exactly 4, because the variance term also shifts as the rate moves). This is the single most useful fact in experiment planning, and it runs both ways: a team that cannot afford 23 days is not choosing to be sloppy, it is discovering that a 0.5 pp effect is not measurable at its traffic. The honest response is to say so up front rather than run underpowered and report a null as "no effect".
from scipy import stats
import numpy as np

def sample_size_per_group(
    baseline_rate=0.10,   # control conversion rate
    mde=0.02,             # min detectable effect (absolute)
    alpha=0.05,           # significance level
    power=0.80            # 1 - beta
):
    effect = mde
    pooled_p = baseline_rate + effect / 2
    pooled_var = 2 * pooled_p * (1 - pooled_p)
    z_alpha = stats.norm.ppf(1 - alpha / 2)
    z_beta  = stats.norm.ppf(power)
    n = (z_alpha + z_beta)**2 * pooled_var / effect**2
    return int(np.ceil(n))

# 10% baseline, want to detect +2pp lift, 80% power
n = sample_size_per_group(0.10, 0.02, 0.05, 0.80)
# n ≈ 3,842 per group (7,684 total)

Practical tip

Run your power analysis before launching the experiment — never stop early because it "looks significant." Peeking inflates Type I error. Pre-register the sample size and run to completion.

Peeking and multiple testing, quantified
These are the two ways an honest team ships a feature that does nothing, and both are arithmetic rather than judgement, so both can be stated exactly.
worked — the cost of looking early

Simulate an A/B test where the null is true: both arms drawn from the same distribution, so every "win" is a false positive. Stop the moment p < 0.05 at any check. 20,000 simulated experiments give the false-positive rate below.

A dashboard refreshed daily for two weeks is not a mild convenience — it turns a 5% error rate into one false win in five. And note the mechanism, because it explains the fix: the sequence of running estimates wanders, so given enough looks it will eventually cross the boundary by chance. The remedy is not "look less"; it is to use a boundary that already accounts for looking — sequential testing (mSPRT, always-valid p-values, group-sequential alpha spending). Those let you stop early legitimately, which is what people wanted in the first place.
Multiple testing is the same arithmetic across metrics instead of across time. With independent tests at α = 0.05, the chance of at least one false positive is $1 - 0.95^k$:

A standard experiment dashboard carries more than 20 metrics, so the coin-flip default is that something on it is significant and meaningless. Designate one primary metric before launch and treat everything else as guardrails or exploration; use Bonferroni (α/k) when you genuinely have a small family of confirmatory tests, and Benjamini–Hochberg FDR when you are screening many. The important half is the pre-registration, not the correction.

SUTVA is the one that invalidates the experiment rather than weakening it. The stable-unit-treatment-value assumption says one user's outcome does not depend on another user's assignment. In a social product, a marketplace, or anything with shared inventory it is false by construction: give half the drivers a better dispatch algorithm and the control drivers get the leftovers, so the control group is damaged by the treatment and the measured lift is partly cannibalisation. Cluster-randomise by city or region, or run a switchback that alternates the whole market over time. The tell is a lift that shrinks as you roll out — the control group stops being harmed and the "gain" evaporates.
And check sample ratio mismatch first, every time. A chi-square on the observed split is brutally sensitive at scale: at 200,000 users per arm a 50.5/49.5 split gives p ≈ 8×10⁻⁶. That is not a rounding artefact, it is a bug — a redirect that drops slow clients, a bot filter applied to one arm, an SDK that fails differently on old Android. If the split is broken, every downstream number is meaningless, so SRM is a gate before analysis rather than a metric alongside it.

The "30–80%" in that first row is not a rule of thumb, it is $\rho^2$. With the optimal coefficient $\theta^* = \operatorname{Cov}(Y,X)/\operatorname{Var}(X)$, the adjusted metric has $\operatorname{Var}(Y^*) = \operatorname{Var}(Y)\,(1-\rho^2)$ where $\rho$ is the correlation between the metric and its pre-experiment value. So the entire benefit is decided by one number you can measure before running anything:

Three things fall straight out of that formula. Sticky per-user metrics benefit enormously — last month's spend predicts this month's, so ρ is high and you roughly double your traffic for free. New users get nothing, because they have no pre-period, which is why CUPED is usually applied to returning users with a separate untreated stratum. And the covariate must be strictly pre-experiment: use anything measured after assignment and you are conditioning on a post-treatment variable, which reintroduces exactly the bias randomisation removed. That last mistake is easy to make and invisible in the output.
CUPED — the most impactful technique

CUPED uses the same metric measured before the experiment as a covariate to remove noise. If last week's revenue predicts this week's, regressing it out dramatically reduces variance. Used by Netflix, Airbnb, Booking.com as standard practice. Requires no change to randomisation — pure post-hoc analysis step.

Part 2 — Observational Causal Inference (When You Can't Randomise)
Difference-in-Differences (DiD)
$$\begin{aligned} \hat{\tau}_{\text{DiD}} &= (\bar{Y}_{T,\text{post}} - \bar{Y}_{T,\text{pre}}) - (\bar{Y}_{C,\text{post}} - \bar{Y}_{C,\text{pre}}) \\ &= \text{change in treated} - \text{change in control} \\ \text{Parallel trends assumption}&: \text{treated and control would have evolved similarly absent treatment} \end{aligned}$$
The idea in one line: the control group's change is your estimate of what the treated group's change would have been. Subtracting it removes anything that shifted both groups — seasonality, a pricing change, a pandemic — and also removes any fixed difference between the groups, which is why the two groups do not need to be comparable in level, only in trend.
Classic example
  • Card & Krueger (1994): New Jersey raised minimum wage (treated); Pennsylvania did not (control)
  • Employment changed differently in NJ vs PA — the difference of differences is the causal effect
  • Key assumption: parallel trends — NJ and PA employment would have moved together absent the policy change
Parallel trends is untestable — it is a claim about a counterfactual period. What you can do is check the pre-period: plot both series for several periods before treatment and run an event study with leads and lags. Significant "effects" before treatment started mean the assumption is already failing. That check is necessary and not sufficient, and saying so is the difference between a defensible estimate and a plausible one.
import statsmodels.formula.api as smf

# DiD regression formulation:
# Y = β0 + β1·post + β2·treated + β3·(post × treated) + ε
# β3 = DiD estimate (causal effect)

result = smf.ols(
    "outcome ~ post + treated + post:treated",
    data=df
).fit()

did_estimate = result.params["post:treated"]
print(f"DiD estimate: {did_estimate:.3f}")
print(f"p-value: {result.pvalues['post:treated']:.4f}")
The interaction coefficient is the estimate — that is why DiD is usually written as a regression rather than four means. It also generalises for free: add unit and time fixed effects for many groups and periods, and cluster standard errors by unit, because outcomes within a unit are correlated over time and ignoring that understates the standard error badly.

MethodKey ideaAssumptionWhen to use
Propensity Score Matching (PSM)Match treated and control units with similar probability of being treated; compare outcomesNo unmeasured confounders (conditional ignorability)Observational study with rich covariates; reduce selection bias
Inverse Propensity Weighting (IPW)Reweight observations by 1/P(treatment) — up-weights rare assignmentsNo unmeasured confounders; positivityAverage treatment effect estimation; works with continuous treatment

Ranked by how much they ask you to believe: RDD asks least — near the cutoff, assignment is close to arbitrary, so it is the nearest thing to a local randomised trial, and its cost is that it only identifies the effect at the threshold. IV asks for an exclusion restriction that is untestable and usually contestable, and returns a LATE — the effect on the compliers, whoever they happen to be — not the ATE. PSM and IPW ask for the strongest thing of all, that you measured every confounder, which is unverifiable and usually false; they also need positivity, meaning every unit had some chance of either arm, and IPW blows up when a propensity approaches 0 or 1, so trim or stabilise the weights. Synthetic control is for the single-treated-unit case and its honest inference is a placebo permutation over the donor pool, not a t-test.
The practical framing for an interview: none of these recovers what randomisation gives you. They convert an unanswerable question into one answerable under a stated assumption, so the deliverable is the estimate plus the assumption plus a sensitivity analysis showing how wrong the assumption would have to be to overturn the conclusion.
Colliders — the bias you create by controlling for something
"Control for more covariates" is the most common piece of bad causal advice. Confounders must be controlled; colliders must not be, and conditioning on one manufactures an association where none exists.
A collider is a variable caused by both of the things you are relating. Condition on it — by controlling for it, stratifying on it, or simply by collecting a sample selected on it — and you open a path between two independent causes.
worked — a correlation conjured from nothing

Draw 200,000 people with independent talent and luck, then admit anyone whose sum exceeds a bar. In the full population the two are uncorrelated: r = −0.001. Among the admitted, r = −0.688. Nobody manipulated anything and no confounder exists — the negative relationship is entirely an artefact of looking only at people who got in, because among them a shortfall in one must be made up by the other. This is why "among our customers, feature use is negatively related to satisfaction" is usually a statement about who becomes a customer.

Two consequences that matter in practice. Selection is conditioning. Restricting to converted users, surviving accounts, or people who answered the survey is controlling for a collider whether or not a regression is involved — so the bias arrives through the sampling frame, silently, with no variable in the model to point at. And the direction is not predictable: collider bias can invent, reverse, or mask an effect, which is why "we added controls and the estimate got smaller, so the effect is real" is not valid reasoning. Draw the DAG first, decide what to condition on from the backdoor criterion, and treat any variable that could plausibly be caused by both treatment and outcome as radioactive — including anything measured after treatment.
Part 3 — Uplift Modelling (Heterogeneous Treatment Effects)
Uplift Modelling — Targeting Who Responds to Treatment
A propensity model ranks who is likely to convert. An uplift model ranks who converts because you intervened. Those rankings are close to unrelated, and the gap between them is usually the entire return on the campaign — because the people most likely to convert are frequently the people who were going to convert anyway.
The four customer segments
SegmentWithout treatmentWith treatmentTarget?
PersuadablesWon't convertWill convert✅ YES — highest ROI
Sure thingsWill convert anywayWill convert❌ Wasted spend
Lost causesWon't convertWon't convert❌ Wasted spend
Do-not-disturbWill convertWon't convert (harmed)🚫 AVOID
A propensity model puts sure things at the top — they have the highest conversion probability — so it spends the budget on people who needed nothing, and cannot see do-not-disturbs at all, because their high propensity looks like a reason to contact them.
Methods
  • Two-model (T-learner): train separate models for treatment and control; uplift = model_T(x) - model_C(x). Simple but high variance
  • S-learner: single model with treatment indicator as feature; uplift = model(x, T=1) - model(x, T=0)
  • X-learner: cross-fitting that handles unequal treatment/control sizes; lower variance than T-learner
  • Causal forests (Wager & Athey): random forest variant that directly targets HTE estimation; gold standard in industry
  • Meta-learners (econML): plug-in estimation; works with any base learner
The reason T-learner is noisy is worth knowing: you are differencing two independently-fitted models, so the errors add while the signal — an uplift of a few percentage points — is far smaller than either model's own error. S-learner has the opposite failure: with a strong feature set, a single model can shrink the treatment indicator toward irrelevance and report almost no uplift anywhere. X-learner and causal forests exist because they target the difference directly instead of subtracting two things fitted for another purpose.

100,000 customers: 15% persuadable (0% → 35% conversion), 25% sure things (80% either way), 55% lost causes (0% either way), 5% do-not-disturb (60% → 35%, actively harmed by contact). Margin £40 per conversion, contact cost £5.

Two things in that table are worth sitting with. The propensity model loses money — it is a competent model of the wrong quantity, spending £150,000 to reach sure things. And treating 30% of the list produces more incremental conversions than treating all of it (5,298 against 4,036), which is not a rounding oddity: the do-not-disturb segment destroys 1,250 conversions that would have happened anyway, so contacting everyone is worse than contacting the right third. That is the case for uplift modelling in one line — the sign of the treatment effect is not constant across people, and any method that estimates only an average is blind to it.

Uplift Evaluation — Qini Curve & AUUC
  • Qini curve: rank individuals by predicted uplift (high to low); plot cumulative actual uplift vs proportion treated. Better model = curve above random diagonal
  • AUUC (Area Under Uplift Curve): scalar summary; higher = better model at targeting persuadables
  • Uplift at decile: compare mean(Y|T=1) - mean(Y|T=0) within each decile of predicted uplift — should be monotonically decreasing
You cannot score an uplift model the way you score a classifier, because the label it predicts — the individual treatment effect — is never observed for anybody. Every metric here works by grouping: rank by predicted uplift, then within each bucket compare treated and control outcomes, which is an achievable measurement because the bucket contains both. This is also why uplift evaluation needs a genuinely randomised holdout: if assignment was not random, the within-bucket difference is confounded and the Qini curve measures selection rather than uplift.
The decile check is the one to run first, and a non-monotonic decile plot means the model is not ranking — a strong AUUC with a ragged decile profile usually indicates overfitting to a few high-variance cells rather than real heterogeneity.
from sklift.metrics import qini_auc_score, uplift_curve

# Compute AUUC
auuc = qini_auc_score(
    y_true=y_test,
    uplift=ite,          # predicted treatment effect
    treatment=t_test     # actual treatment assignment
)
print(f"AUUC: {auuc:.4f}")
Part 4 — DoWhy & Causal Graphs
DoWhy — Microsoft's Causal Inference Library
DoWhy implements Pearl's causal framework: specify a causal graph (DAG), identify whether the causal effect is estimable from data, estimate it, and test robustness of the estimate.
The reason the library is shaped in four steps — model, identify, estimate, refute — is that it forces the order most analyses get wrong. Identification comes before estimation: you first ask whether the effect is recoverable from the data you have given the graph you drew, and only then pick an estimator. Most bad causal work runs a regression and then argues about what it means.
import dowhy
from dowhy import CausalModel

model = CausalModel(
    data=df,
    treatment="ad_exposure",
    outcome="purchase",
    # Specify causal graph as GML or dot notation
    # Confounders: age, income affect both ad targeting AND purchase
    common_causes=["age", "income", "browsing_history"],
    instruments=["random_ad_slot"]  # instrumental variable
)

# Step 1: Identify — can we estimate the effect from observables?
identified_estimand = model.identify_effect(
    proceed_when_unidentifiable=True
)

# Step 2: Estimate using the identified strategy
estimate = model.estimate_effect(
    identified_estimand,
    method_name="backdoor.linear_regression"
    # also: "iv.instrumental_variable", "backdoor.propensity_score_matching"
)
print(f"Causal effect: {estimate.value:.4f}")

# Step 3: Refute — test sensitivity to assumptions
refute = model.refute_estimate(
    identified_estimand, estimate,
    method_name="random_common_cause"  # add random confounder; effect should not change
)
print(refute)
Causal graph concepts
  • DAG (Directed Acyclic Graph): nodes = variables, edges = direct causal relationships
  • Confounder: common cause of treatment and outcome — must be controlled
  • Collider: common effect of treatment and outcome — must NOT be controlled (conditioning opens a spurious path)
  • Backdoor criterion: a set of variables that blocks all backdoor paths from treatment to outcome and is not a descendant of treatment
  • Front-door criterion: estimate causal effect via mediators when confounders are unobserved
A mediator is the third case and it is distinct from both: it sits on the causal path, so controlling for it removes part of the effect you are trying to measure. Confounder — control. Collider — never. Mediator — only if you specifically want the direct effect, and then say so.
DoWhy refutation tests
TestWhat it checks
Random common causeAdd random confounder — estimate should barely change
Placebo treatmentReplace treatment with random variable — effect should be ~0

Sensitivity (Rosenbaum bounds)How strong would unmeasured confounder need to be to explain away the effect?
These are falsification tests, not validation. Passing them does not make an estimate causal — it fails to disprove it. The genuinely informative one is the last: reporting "an unmeasured confounder would need to be more strongly associated with both treatment and outcome than any variable we measured" is a claim a reviewer can argue with, which is exactly what makes it worth stating.
Mistakes that survive code review
  • Peeking, then reporting nominal α. Ten looks turns 5% into 19.9%. If you want to stop early, use a method designed for it — mSPRT or alpha spending — rather than the same t-test applied more often
  • No pre-registered primary metric. Twenty metrics at α = 0.05 give a 64% chance of at least one false win. The dashboard will always have a green cell
  • Analysing before checking SRM. A 50.5/49.5 split at 200k per arm is p ≈ 8×10⁻⁶ — a bug, not noise. Every downstream estimate is void until it is explained
  • Statistical significance read as business significance. At n = 10M a 0.01 pp lift is significant and worthless. Report the effect size and its confidence interval; decide against the MDE you committed to beforehand
  • Underpowered null read as "no effect". Absence of evidence is not evidence of absence — quote the confidence interval, and if it spans effects you would have shipped, the honest conclusion is that the test could not tell
  • Ignoring SUTVA in networked or marketplace products. The control group is damaged by the treatment, so the lift is partly cannibalisation. Cluster-randomise or switchback
  • Controlling for a collider or a post-treatment variable. Adding controls can create bias as easily as remove it, and selecting the sample on an outcome does the same thing invisibly
  • CUPED on a covariate measured after assignment. It is no longer pre-experiment, so it reintroduces the bias randomisation removed — and nothing in the output looks wrong
  • Observational uplift without propensity adjustment. Self-selected treatment means treated and untreated differ systematically; the "uplift" is selection
  • Quoting a quasi-experimental estimate as if it were an experiment. DiD, IV and RDD each buy an answer with an assumption. State it, test what can be tested, and report how much it would have to be violated to change the decision
  • Targeting a campaign with a propensity model and calling it personalisation. It ranks the wrong quantity; on the worked example above it turns a £62k profit into a £108k loss
How It's Used at Top Companies
  • Netflix: CUPED variance reduction as standard practice on all A/B tests; causal forests for personalised recommendation treatment effects
  • Airbnb: DiD for evaluating policy changes (e.g. host cancellation policy) where randomisation is infeasible; SUTVA-aware cluster experiments for marketplace interventions
  • Booking.com: runs 1,000+ concurrent A/B tests; CUPED + sequential testing to manage multiple comparisons and early stopping

🎯 In an interview

Open on seeing versus doing. "Correlation is $P(Y \mid X)$ — what I expect having observed X. Causation is $P(Y \mid do(X))$ — what I expect having set X. They differ when a confounder drives both, when the arrow runs the other way, or when I am selecting on the outcome. Randomisation makes them equal because assignment is independent of everything, measured or not, and every observational method is a different argument for why they are equal conditional on something."

Design an A/B test in five steps, with the number that shows you have run one. "Pick one primary metric and the MDE worth detecting. Power-analyse: from a 10% baseline, a 2 pp MDE needs about 3,800 per arm, 1 pp needs 14,700, and 0.5 pp needs 57,800 — n scales as 1/δ², so halving the MDE roughly quadruples the traffic. Randomise, by cluster if the product has network effects. Run to the pre-registered n. Then analyse: check sample ratio mismatch first, then effect size with a confidence interval, not just a p-value."

Be exact about peeking, because everyone claims to know it. "Ten looks at a two-week test takes the false-positive rate from 5% to about 20% — a one-in-five chance of shipping nothing. The fix is not discipline, it is a boundary that accounts for looking: mSPRT or alpha spending. Same arithmetic across metrics — 20 metrics at α = 0.05 gives a 64% chance of at least one false win, which is why the primary metric is designated before launch."

On CUPED, give the formula rather than the folklore. "Variance drops by $1-\rho^2$ where ρ is the correlation with the pre-experiment value of the same metric, so ρ = 0.7 nearly doubles effective sample size. It changes nothing about randomisation — it is a post-hoc adjustment — but the covariate must be strictly pre-assignment, or you have conditioned on a post-treatment variable and put the bias back."

Have the uplift answer ready, because it separates candidates. "A propensity model ranks who will convert; an uplift model ranks who converts because of the treatment. Targeting by propensity spends the budget on people who would have converted anyway, and it cannot see the segment you actively harm by contacting. On a realistic segment mix, targeting the top 30% by uplift earns money while targeting the top 30% by propensity loses it — and treating the right third beats treating everyone on incremental conversions, because the do-not-disturb group has a negative effect."

What not to say. Never call a quasi-experimental estimate causal without naming its assumption — parallel trends for DiD, exclusion for IV, no sorting for RDD — and note that IV gives a LATE on compliers, not the ATE. Do not offer "control for more variables" as the fix for confounding: colliders exist, and conditioning on one manufactured an r of −0.69 between two independent variables in the example above. Do not report a null from an underpowered test as "no effect". And do not say a p-value is the probability the hypothesis is true.

A confounder pointing at both treatment and outcome
In code
Correlation, the confounded estimate, and the adjusted estimate on data where the true effect is known. Simpson’s paradox in eight lines.
import numpy as np, pandas as pd
import statsmodels.formula.api as smf

rng = np.random.default_rng(0)
n = 20_000
# Confounder: severity drives BOTH treatment and outcome
severity = rng.normal(size=n)
treated = (rng.random(n) < 1/(1+np.exp(-1.5*severity))).astype(int)   # sicker -> treated
outcome = 2.0*treated - 3.0*severity + rng.normal(0, 1, n)            # TRUE effect = +2.0
df = pd.DataFrame(dict(y=outcome, t=treated, sev=severity))

print("naive difference     ", round(df[df.t==1].y.mean() - df[df.t==0].y.mean(), 3))
print("adjusted (regression)", round(smf.ols('y ~ t + sev', df).fit().params['t'], 3))
# The naive number is NEGATIVE despite a positive true effect: the treatment
# looks harmful only because it is given to sicker people.

# A/B testing: fix the sample size BEFORE looking, or peeking pushes the
# false-positive rate well past 5%.
from statsmodels.stats.power import NormalIndPower
from statsmodels.stats.proportion import proportion_effectsize
n_needed = NormalIndPower().solve_power(
    effect_size=proportion_effectsize(0.10, 0.11),      # 10% -> 11%
    alpha=0.05, power=0.80, alternative='two-sided')
print(f"n per arm for a +1pp lift: {int(np.ceil(n_needed)):,}")
