The round that eliminates people who can model. Three things are actually being tested: whether you reach for a vectorised operation instead of a loop, whether you know the window functions that replace the self-join you were about to write, and whether your validation code can be trusted. The third one matters long after the interview — the difference between a pipeline and a hand-rolled cross-validation is the difference between an honest score and a fictional one, and the example below scores 0.892 AUC on pure noise to prove it.

The advice to "vectorise" is usually given without a number, which makes it sound like style. It is not style. Computing a * b over 200,000 rows, timed three ways:
ApproachTimeVersus vectorised
df.a * df.b~0.1 ms1×
loop over df.itertuples()~60 ms~500–700× slower
df.apply(..., axis=1)~1,240 ms~10,000× slower
Absolute timings vary by machine and run; the ordering and the order of magnitude do not
Note which one is worst. Row-wise apply reads as idiomatic pandas and is dramatically slower than the explicit loop people are embarrassed to write, because it builds a Series object for every row on top of the same per-row Python dispatch. apply(axis=1) is not a vectorised operation with nicer syntax — it is a loop with overhead, and treating it as the "proper pandas way" is the most common version of this mistake.
The reason vectorised operations win is that the loop moves into C over a contiguous typed buffer: no per-element boxing, no interpreter dispatch, and the memory access pattern is one the CPU can prefetch. That also tells you when the advice stops applying — if the per-row work is genuinely irreducible Python (calling an API, parsing irregular text), vectorising buys nothing, and the answer is to reduce the number of rows or move to a real parallel framework rather than to keep looking for a clever one-liner.
SQL — Data Science Patterns
🗃️ SQL
-- Running average payment rate (window function)
SELECT customer_id, month,
  AVG(payment_ratio) OVER (PARTITION BY customer_id
    ORDER BY month ROWS BETWEEN 2 PRECEDING AND CURRENT ROW) AS rolling_3m_rate
FROM payments;

-- Cohort retention analysis
SELECT cohort_month, months_since_join,
  COUNT(DISTINCT user_id) AS retained_users,
  COUNT(DISTINCT user_id) * 1.0 / FIRST_VALUE(COUNT(DISTINCT user_id))
    OVER (PARTITION BY cohort_month ORDER BY months_since_join) AS retention_rate
FROM user_cohorts
GROUP BY cohort_month, months_since_join;

-- Customers who defaulted within 6 months of application
SELECT a.customer_id, a.app_date, d.default_date
FROM applications a
LEFT JOIN defaults d ON a.customer_id = d.customer_id
  AND d.default_date BETWEEN a.app_date AND a.app_date + INTERVAL '6 months'
WHERE d.customer_id IS NOT NULL;
Window functions are the whole SQL interview. The tell that someone learned SQL before about 2010 is a correlated subquery or a self-join where a window would do — and the difference is not only readability. A self-join to find "each row's previous value" scans the table twice and can degrade badly with group size; LAG() does it in one ordered pass.
QuestionWindow functionWhat it replaces
Top N per groupROW_NUMBER() OVER (PARTITION BY g ORDER BY x DESC)correlated subquery with LIMIT
Previous / next valueLAG(x) / LEAD(x)self-join on t.n = t2.n - 1
Running total or rolling meanSUM/AVG(x) OVER (ORDER BY d ROWS BETWEEN n PRECEDING AND CURRENT ROW)a join to a date-range subquery
Share of group totalx / SUM(x) OVER (PARTITION BY g)join back to a GROUP BY aggregate
Deduplicate, keep latestROW_NUMBER() then WHERE rn = 1DISTINCT ON or a max-date self-join
Two distinctions that get asked as follow-ups. RANK leaves gaps after ties, DENSE_RANK does not, and ROW_NUMBER breaks ties arbitrarily — so "top 3 per group" with ties is genuinely three different answers and the right one depends on whether ties should all be kept. And ROWS counts rows while RANGE counts values: on a table with gaps in the dates, ROWS BETWEEN 6 PRECEDING gives you the last 6 rows, not the last 6 days, which quietly produces the wrong rolling window whenever data is missing.
One correctness trap worth naming because it shows up in real feature pipelines: in the last query above, the date filter sits in the ON clause rather than the WHERE. On a LEFT JOIN those are not the same — a predicate on the right table in WHERE discards the unmatched rows and silently converts the LEFT JOIN into an INNER JOIN, dropping exactly the customers who never defaulted. That is the negative class disappearing from a training set without an error.

Nearly all of these are one idea: replace a scan with a lookup, or a sort with a partial order. Hashmap counting turns a nested search into a single pass; sliding window reuses the previous window's answer instead of recomputing it; a heap maintains the top-k without sorting the other n−k. If you can say which of those you are doing and why it changes the complexity class, you have answered the question the interviewer is actually asking.
The in operator is where this becomes concrete, because it looks identical on a list and a set and is not:
2,000 membership tests against 1,000,000 itemsTimeComplexity
x in big_list~6,700 msO(n) per test
x in big_set~0.1 msO(1) per test
One character of difference in the type, and roughly five orders of magnitude in the runtime
Worth having ready: dict and set lookup, and list.append, are O(1) (append amortised); sorting is O(n log n); list.insert(0, x) and del list[0] are O(n) because everything shifts — use collections.deque when you need to push and pop at both ends. And the reason the sliding-window pattern uses a deque rather than a list is exactly that: the window's left edge is a pop from the front.
Worked — the leak that makes a pipeline non-negotiable
Generate 200 rows and 5,000 features of pure Gaussian noise, with labels drawn at random. There is no signal whatsoever; the true AUC of any model is 0.50. Now select the 20 features most correlated with the label, then cross-validate — the sequence almost everyone writes the first time.
Procedure5-fold CV AUCVerdict
SelectKBest on the full data, then cross_val_score0.892fiction — there is no signal to find
Pipeline([SelectKBest, LogisticRegression]) inside CV0.557honest, and near 0.50 as it should be
The mechanism is that the selection step saw the validation labels. With 5,000 noise features and 200 rows, some will correlate with the labels by luck; picking them using all the data bakes that luck into every fold, so the "held-out" rows were used to choose the features being tested on them. The score is not slightly optimistic — it is 0.892 on data containing nothing, which would comfortably pass a review and reach production.
The same run makes an honest second point that the usual advice glosses over. Fitting a StandardScaler on the full dataset moved the score by essentially nothing (0.496 either way), because a mean and a variance estimated from a few hundred extra rows barely differ. So the risk is not uniform: leakage scales with how much the preprocessing step depends on the labels and how many choices it makes. Scaling is nearly harmless, imputation slightly worse, and anything supervised — feature selection, target encoding, resampling, threshold tuning — is catastrophic. Put everything in the pipeline anyway, because the rule is easier to follow than the exceptions are to remember.
Two consequences for real code. A Pipeline refits every step on each training fold, which is the only reason cross_val_score means anything — and it also serialises preprocessing and model as one artifact, which removes an entire class of training–serving skew. And if the data has a time order, use TimeSeriesSplit: a shuffled K-fold trains on the future to predict the past, which is a leak the pipeline cannot save you from.
PyTorch Essential Patterns
🐍 Python
import torch, torch.nn as nn

# Define model
class MLP(nn.Module):
    def __init__(self):
        super().__init__()
        self.net = nn.Sequential(
            nn.Linear(128, 64), nn.ReLU(), nn.Dropout(0.3),
            nn.Linear(64, 1), nn.Sigmoid()
        )
    def forward(self, x):
        return self.net(x)

# Training loop
model = MLP(); optimizer = torch.optim.AdamW(model.parameters(), lr=1e-3)
for epoch in range(epochs):
    model.train()
    for X_batch, y_batch in dataloader:
        optimizer.zero_grad()
        pred = model(X_batch)
        loss = nn.BCELoss()(pred, y_batch)
        loss.backward()
        nn.utils.clip_grad_norm_(model.parameters(), 1.0)  # gradient clip
        optimizer.step()
Mistakes that survive code review
  • Preprocessing fitted outside the CV loop. On pure noise this scored 0.892 against a true 0.50. Supervised steps — selection, target encoding, resampling — are the catastrophic ones; put every step in the Pipeline
  • Shuffled K-fold on time-ordered data. Training on the future to predict the past. TimeSeriesSplit, and a pipeline will not protect you from this one
  • df.apply(axis=1) mistaken for vectorisation. Around four orders of magnitude slower than the vectorised expression here — and slower than the explicit loop it is meant to replace
  • Membership tests against a list. One character between in list and in set, and about five orders of magnitude in runtime at a million items
  • A filter on the right table in WHERE after a LEFT JOIN. It silently becomes an INNER JOIN and drops the unmatched rows — in a training set, that is the negative class disappearing. Put the predicate in ON
  • ROWS where RANGE was meant. "6 preceding rows" is not "6 preceding days" once dates are missing, and the rolling feature is quietly wrong
  • Self-joins and correlated subqueries where a window function fits. Slower, and read as unfamiliarity with anything after SQL-92
  • RANK vs DENSE_RANK vs ROW_NUMBER chosen by habit. With ties they give three different answers to "top 3 per group"
  • list.insert(0, x) in a loop. O(n) per call, so O(n²) overall. collections.deque is O(1) at both ends
  • Chained indexing assignment — df[mask]['col'] = value writes to a temporary and silently does nothing. Use df.loc[mask, 'col'], and .copy() when you intend a new frame
  • Optimising before profiling. %timeit first — the slow line is regularly not the one you expected, and in ML code it is often I/O rather than compute

🎯 In an interview

Say what you are doing before you type, and name the complexity. "I'll use a hashmap so lookups are O(1) instead of scanning — that takes this from O(n²) to O(n)." Interviewers are scoring the reasoning; the syntax is the easy part, and narrating the trade-off is what distinguishes a candidate who has thought about it from one who has memorised the pattern.

Have one vectorisation number. "On 200,000 rows I measured about 0.1 ms vectorised, 60 ms for an itertuples loop, and 1.2 seconds for apply(axis=1) — apply is the slowest, because it builds a Series per row on top of the same Python dispatch. That's the one people get wrong: it looks like idiomatic pandas and it is a loop with overhead."

On SQL, lead with windows and know the edge cases. "Top-N-per-group, previous value, running total and share-of-total are all window functions — ROW_NUMBER, LAG, SUM OVER — and they replace self-joins that scan the table twice. Then the two follow-ups: RANK gaps after ties while DENSE_RANK doesn't, and ROWS counts rows while RANGE counts values, so a rolling 7-day window written with ROWS is wrong as soon as a date is missing."

If they ask about validation, tell the noise story. "Two hundred rows, five thousand pure-noise features, random labels — true AUC 0.50. Select the best 20 features on the full data and then cross-validate and you get 0.892. Put the selection inside a Pipeline and you get 0.557. The selection step saw the validation labels. And it's worth being precise about the risk: fitting a scaler on all the data barely moved the number, but anything supervised is catastrophic — which is why the rule is 'every step in the pipeline' rather than a list of exceptions."

What not to say. Do not say "I'll loop over the rows" — it ends the conversation. Do not treat apply(axis=1) as the vectorised option. Do not claim a pipeline prevents all leakage: it does not touch temporal leakage, and shuffled K-fold on time-ordered data trains on the future regardless. And do not optimise a line you have not timed — say "I'd profile first", and mean it.

Complexity classes, and where a dataframe loop lands
In code
The leak, reproduced end to end — and the two timings that make "vectorise" a measurement rather than an opinion.
import numpy as np, pandas as pd, time
from sklearn.feature_selection import SelectKBest, f_classif
from sklearn.linear_model import LogisticRegression
from sklearn.pipeline import Pipeline
from sklearn.model_selection import cross_val_score, StratifiedKFold

# ---- 1. LEAKAGE: pure noise, random labels, so the TRUE AUC is 0.50 --------
rng = np.random.default_rng(0)
n, p = 200, 5_000
X = rng.normal(size=(n, p))
y = rng.integers(0, 2, n)                      # independent of X
cv = StratifiedKFold(5, shuffle=True, random_state=0)

# WRONG: the selector sees every label, including the held-out folds'
X_sel = SelectKBest(f_classif, k=20).fit_transform(X, y)
wrong = cross_val_score(LogisticRegression(max_iter=1000), X_sel, y,
                        cv=cv, scoring='roc_auc').mean()

# RIGHT: every step refit inside each training fold
pipe = Pipeline([('sel', SelectKBest(f_classif, k=20)),
                 ('clf', LogisticRegression(max_iter=1000))])
right = cross_val_score(pipe, X, y, cv=cv, scoring='roc_auc').mean()

print(f"selection before CV : {wrong:.3f}   <- fiction")      # 0.892
print(f"selection in Pipeline: {right:.3f}   <- the truth")    # 0.557
# Leakage scales with how much the step depends on the LABELS. A StandardScaler
# fitted on all the data barely moves this; anything supervised is catastrophic.

# ---- 2. VECTORISATION: same computation, three ways -----------------------
df = pd.DataFrame({'a': rng.normal(size=200_000), 'b': rng.normal(size=200_000)})
def timed(f, reps=1):
    s = time.perf_counter()
    for _ in range(reps): f()
    return (time.perf_counter() - s) / reps * 1000          # ms

vec   = timed(lambda: df.a * df.b, reps=20)
loop  = timed(lambda: [r.a * r.b for r in df.itertuples()])
apply = timed(lambda: df.apply(lambda r: r.a * r.b, axis=1))
print(f"vectorised {vec:8.2f} ms | itertuples {loop:8.1f} ms ({loop/vec:,.0f}x)"
      f" | apply {apply:8.1f} ms ({apply/vec:,.0f}x)")
# apply(axis=1) is the SLOWEST -- it builds a Series per row. It is a loop.

# ---- 3. O(1) vs O(n): one character of difference in the type -------------
big, probes = list(range(1_000_000)), rng.integers(0, 1_000_000, 2_000).tolist()
as_set = set(big)
print(f"list {timed(lambda: sum(x in big for x in probes)):.0f} ms vs "
      f"set {timed(lambda: sum(x in as_set for x in probes), reps=20):.3f} ms")
