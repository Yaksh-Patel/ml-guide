Random Forest
Bagging plus one deliberately strange idea: handicap every tree by hiding most of the features from it at each split. Each tree gets measurably worse, and the average gets much better. Understanding why a handicap improves the ensemble is the whole topic — and it is one formula.
The formula that explains the entire algorithm
Average B trees, each with variance σ² and pairwise correlation ρ with the others. The variance of the average is not σ²/B — that is only true if the trees are independent, and trees fitted to the same data are anything but.
$$\operatorname{Var}\!\left(\frac{1}{B}\sum_{b=1}^{B} T_b\right) = \underbrace{\rho\sigma^2}_{\text{floor — no fix by adding trees}} + \underbrace{\frac{1-\rho}{B}\sigma^2}_{\text{vanishes as } B \to \infty}$$
Read the two terms. The right one is what averaging buys, and it goes to zero if you are patient. The left one does not depend on B at all. Adding trees forever cannot push the variance below ρσ² — so once B is large, the only lever left is ρ. That is the insight the algorithm is named for.
Put σ² = 1 and B = 500 through it:
Methodρ between treesVariance of the average
Bagging — every feature available at every split≈ 0.700.70 + 0.30/500 = 0.7006
Random Forest — √d features per split≈ 0.300.30 + 0.70/500 = 0.3014
Same trees, same data, same 500 of them — less than half the variance. The only change is that each split may only look at a random handful of features. That single line of arithmetic is the argument for Random Forest over bagging, and it is what to reach for when someone asks why the feature subsampling matters.
why hobbling each tree wins

Restricting features raises each individual tree's error — σ² goes up a little, because a tree denied its best feature must settle for a worse split. But ρ falls a lot, because trees can no longer all seize the same dominant feature at the root and end up as near-copies. The ensemble trades a small rise in the term that averages away for a large fall in the term that never does. With one strong predictor and many weak ones, bagged trees nearly all split on it first and you have effectively averaged 500 copies of one tree.

Two sources of randomness, and the 63.2% nobody derives
1 — Bootstrap the rows. Each tree trains on n rows drawn with replacement. The fraction of the dataset a given tree actually sees is a limit worth doing once rather than memorising. The chance a specific row escapes one draw is (1 − 1/n); over n draws:
$$\left(1-\frac{1}{n}\right)^{n} \xrightarrow{\ n \to \infty\ } e^{-1} = 0.368$$
So ~36.8% of rows are left out of any given tree and ~63.2% are in. The excluded rows are that tree's out-of-bag sample, and they are the reason a forest can validate itself.
2 — Subsample the features at every split. Not once per tree — once per node. At each split the tree may consider only a random √d features (classification) or d/3 (regression). With d = 100 that is 10 candidates per split, so a dominant feature is simply unavailable at roughly 90% of nodes, forcing other trees to discover whatever secondary structure exists. This is the ρ-reducing mechanism made concrete.
OOB error, and the reason it reads slightly low

Every row is out-of-bag for about 36.8% of the trees, so with 500 trees each row receives an honest prediction from roughly 184 of them that never saw it. Averaged over all rows that is a genuine held-out estimate, free, with no second fit.

It is mildly pessimistic for two compounding reasons: each OOB prediction comes from a ~184-tree sub-forest rather than the full 500, and every tree in it was trained on 63.2% of the data rather than all of it. You are grading a smaller forest trained on less data, so the real model is a little better than OOB says. Fine as a tuning signal and for model selection; run proper CV when you need to report a number, especially at small n where the gap widens.

Why deep trees are correct here and wrong in boosting. Averaging reduces variance and does nothing about bias. So the ideal base learner for a forest is low-bias and high-variance — a fully grown tree — and the ensemble cleans up the variance afterwards. Cap the depth and you inject bias that no amount of averaging can remove.
Boosting inverts every part of this. Each tree fits the residual of the ones before it, so the ensemble reduces bias, and its base learners are deliberately shallow and high-bias (depth 3–6). Random Forest averages independent estimates of the same quantity; boosting composes corrections to a running one. That is why one saturates harmlessly as trees are added and the other eventually starts fitting noise and needs early stopping. If you remember one contrast between the two families, this is the one.
Feature importance: three options, and a trap in the safe one
  • Impurity / MDI (feature_importances_) — mean impurity decrease across all trees. Free, and it inherits the cardinality bias in full: continuous and high-cardinality columns offer far more candidate thresholds, so they accumulate gain by opportunity. Measured on training data, so it rewards overfitting. A random ID column will rank well
  • Permutation importance — shuffle one column, measure the score drop on held-out or OOB data. Model-agnostic, no cardinality bias, and the sensible default
  • SHAP (TreeSHAP) — exact and fast for trees, additive per prediction, and the only option that is both local and global
the correlated-feature trap that catches permutation too

Permutation importance fixes the cardinality bias but not correlation, and it fails in a direction people find surprising. Duplicate a genuinely important feature. Permute the first: the forest simply reads the copy, the score barely moves, and the first looks unimportant. Permute the second: the same thing. Both critical features report near-zero importance, and neither result is a bug.

Permutation answers "could the model manage without this column, given the others" — which is not the question most people think they are asking. With correlated features, cluster them and permute each cluster as a unit, or read grouped SHAP values.

Whichever you use, importance is a statement about the model, not about the world. It says where this forest leaned, not what causes the outcome.
Mistakes that survive code review
  • Capping max_depth to "prevent overfitting". Imports a habit from single trees that is actively wrong here. Averaging handles the variance; the depth cap only adds bias. Tune max_features instead — it is the parameter with a floor attached
  • Worrying that more trees will overfit. They cannot. More trees shrink one term monotonically toward ρσ² and never past it. That is boosting's problem, not this one, and confusing the two is the most common tree-ensemble error
  • Quoting feature_importances_. The most-cited and least-correct importance in circulation. Use permutation on held-out data or SHAP — and when features are correlated, group them first
  • Trusting OOB on time-series data. Bootstrapping shuffles the timeline, so every tree trains on rows from after the ones it is scored against. OOB will look excellent and mean nothing. Temporal data needs a forward-chaining split, full stop
  • Expecting calibrated probabilities. A forest's score is a vote share, and averaging bounded votes pulls it away from 0 and 1 — systematically under-confident at the extremes. Fine for ranking; recalibrate before multiplying by money
  • Assuming it extrapolates. It averages leaf means, so like any tree model it is capped by the training range. A forest cannot forecast a trend past what it has seen
  • Ignoring the memory cost. 500 fully grown trees on a million rows is a large object — often hundreds of megabytes to gigabytes. It surprises people at deployment, and it is the usual reason a forest that trained fine cannot be served. min_samples_leaf shrinks it substantially at little accuracy cost
  • Reaching for it on very wide sparse data. Text with 50,000 TF-IDF columns is the case where √d subsampling means most splits see nothing informative. Linear models and boosting handle sparsity far better
Why it survived XGBoost
  • It is the model that works before you have tuned anything. Defaults are close to optimal, the failure modes are mild, and it is genuinely hard to get a badly broken result. That is why AutoML systems and internal platforms still use it as the first baseline — it establishes what the problem is worth before anyone spends a week on boosting
  • Embarrassingly parallel. Trees are independent, so training scales linearly across cores with no coordination. Boosting is sequential by construction — tree k needs tree k−1's residuals. On a big machine with a deadline that difference is decisive
  • Validation for free. OOB removes an entire fold-management step from the loop. When you are sweeping a hundred configurations, skipping k-fold each time is a real saving
  • Wide biological data. Tens of thousands of correlated SNPs or gene-expression features with a few hundred samples: feature subsampling spreads attention across correlated groups instead of locking onto one member, and the importances (read as clusters, not individually) are used as the selection step itself
  • As the reliable second opinion. When a boosted model behaves strangely, a forest on the same features tells you whether the problem is in the data or in the boosting configuration. Different bias, different failure modes, minutes to fit
  • Where XGBoost genuinely wins: peak accuracy on large tabular data, native categorical and missing handling, and probabilities you can almost use directly. If someone is scoring a leaderboard, they are not using a forest — and if someone needs a dependable answer by Friday, they might be
🎯 In an interview

Lead with the variance formula. "Averaging B correlated trees gives ρσ² + (1−ρ)σ²/B. The second term vanishes as you add trees; the first does not. So beyond a few hundred trees the only remaining lever is the correlation between them — and that is exactly what per-split feature subsampling attacks." Then the numbers: ρ = 0.7 for bagging versus 0.3 for a forest is 0.70 against 0.30 variance at 500 trees. This answer is the topic.

Expect: "Why 63.2%?" — Derive it rather than recite it: the chance a row survives n draws with replacement is (1 − 1/n)ⁿ → 1/e ≈ 0.368 left out, so 63.2% in. Follow with why OOB is slightly pessimistic — each row is scored by only ~37% of the trees, each trained on 63% of the data.

Expect: "Can Random Forest overfit with more trees?" — No, and say why: more trees only shrink the (1−ρ)σ²/B term toward an asymptote. Then draw the contrast, because it is what the question is really probing: boosting fits residuals sequentially, so its added trees reduce bias and can eventually fit noise, which is why it needs early stopping and a forest does not.

The one that separates people: "Should I limit max_depth?" — No. Averaging removes variance, not bias, so you want low-bias base learners and let the ensemble do its job. Note that boosting is the exact opposite — deliberately shallow, high-bias trees — because it attacks bias instead. Do not say "I use feature_importances_" without naming its cardinality bias, and do not claim RF probabilities are calibrated.

In code
Two independent sources of decorrelation — bootstrap rows and random feature subsets — plus the out-of-bag estimate, which gives you validation for free.
import numpy as np
from sklearn.datasets import load_breast_cancer
from sklearn.ensemble import RandomForestClassifier
from sklearn.inspection import permutation_importance
from sklearn.model_selection import train_test_split

X, y = load_breast_cancer(return_X_y=True)
Xtr, Xte, ytr, yte = train_test_split(X, y, test_size=.25, random_state=0)

rf = RandomForestClassifier(n_estimators=500, max_features='sqrt',
                            oob_score=True, n_jobs=-1, random_state=0).fit(Xtr, ytr)
print(f"oob  {rf.oob_score_:.4f}   test {rf.score(Xte, yte):.4f}")
# OOB uses the ~37% of rows each tree never saw: a free validation set

# max_features is the knob that actually matters. 1.0 = bagged trees, all
# correlated; sqrt(p) decorrelates them and is why a forest beats bagging.
for mf in ('sqrt', 'log2', 0.5, 1.0):
    m = RandomForestClassifier(300, max_features=mf, oob_score=True,
                               n_jobs=-1, random_state=0).fit(Xtr, ytr)
    print(f"  max_features={str(mf):5} oob={m.oob_score_:.4f}")

# Prefer permutation importance: impurity importance is biased by cardinality
perm = permutation_importance(rf, Xte, yte, n_repeats=10, random_state=0)
top = perm.importances_mean.argsort()[::-1][:5]
print("top by permutation:", [load_breast_cancer().feature_names[i] for i in top])
