Deployment & Monitoring (MLOps)
A model becomes a service when four things exist: a pinned artifact you can identify and rebuild, a contract at the edge that rejects bad input loudly, a monitor that can wake someone up, and a rollback you have actually executed. Everything else in this topic is a variation on those four. The reason MLOps is harder than ordinary deployment is that a model is a function of data as well as code, so it can break while every test passes, every service stays green, and nothing in the logs changes — the failure mode is silence, and the discipline is about converting silence into signal.
Part 1 — Serving Patterns & Infrastructure

The question that picks the row is not "how fast can we be" but "is a human waiting, and what happens if we are late?" A checkout fraud decision must return before the payment times out, so the latency is a hard constraint and the model is chosen to fit it. A churn score consumed by tomorrow's email campaign has no such constraint, and building it as a real-time API is pure cost. Batch is the correct default; real-time serving is what you escalate to when a person or a transaction is blocked on the answer.
Serverless deserves its caveat: a cold start that loads a multi-hundred-megabyte model can take many seconds, so the "cold: >1s" in that table is optimistic for anything but small models. It suits genuinely sporadic traffic — and traffic that is sporadic but latency-sensitive is the one combination it serves badly.
Containerisation with Docker
Container = reproducible, portable unit. Packages model + dependencies + runtime together. The standard unit of ML deployment.
  • Dockerfile layers: base image → system deps → Python deps → model artifacts → entrypoint
  • Multi-stage builds: build stage (large) → runtime stage (slim) — reduces final image size 5–10×
  • CUDA base images: use nvidia/cuda:12.x-runtime for GPU serving; don't include cudnn unless needed
  • Model weight mounting: mount weights as a volume or pull from S3/GCS at startup — don't bake into image (large image → slow CI)
  • Health checks: /health endpoint critical for Kubernetes liveness probes
The layer order in that first bullet is the build-time optimisation that matters: Docker caches layers, so anything that changes often must come last. Dependencies change monthly and model weights change weekly, so weights after deps means a retrain rebuilds one small layer instead of reinstalling CUDA. And a container is only reproducible if the versions are pinned — pip install -r requirements.txt with unpinned ranges produces a different image next Tuesday, which is exactly the class of bug containers were adopted to eliminate. Pin a lockfile, and pin the base image by digest rather than by tag.
Kubernetes for ML Serving
Kubernetes ML serving: requests → LoadBalancer → Pods → model servers with HPA scaling
  • Deployment: defines desired Pod spec (image, resources, env vars); rolling updates with zero downtime
  • Service: stable DNS name + load balances across Pods; ClusterIP for internal, LoadBalancer for external
  • HPA: scales Pod count based on CPU/GPU utilisation or custom metrics (requests/sec)
  • Resource requests/limits: always set both — prevents noisy neighbours from starving model Pods
  • GPU node pools: separate node pool with GPU nodes; taint + toleration ensures only GPU Pods schedule there
  • Readiness probe: Kubernetes only routes traffic after probe succeeds — critical for slow model loading
  • ConfigMaps / Secrets: inject model config and API keys without rebuilding images
  • Namespace separation: staging vs production namespaces prevent accidental cross-contamination
Two probes, two different jobs, and confusing them causes a specific outage. The readiness probe controls whether a Pod receives traffic; the liveness probe controls whether it gets killed and restarted. A model that takes 90 seconds to load its weights needs a readiness probe so traffic waits — and if the liveness probe's timeout is shorter than the load time, Kubernetes kills the Pod mid-load, restarts it, and the deployment never converges. Use a startup probe, or a liveness threshold generous enough to cover cold model loading.
Autoscaling on CPU is the wrong signal for GPU inference. A GPU-bound server can sit at 30% CPU while the GPU saturates and latency doubles, so the HPA never scales. Scale on a metric that tracks the actual bottleneck — requests per second, queue depth, or GPU utilisation via a custom metrics adapter. And remember that scaling out has a lead time: a new Pod must be scheduled, pull an image, and load weights, which can be minutes for a large model. Autoscaling absorbs gradual growth; it does not absorb a spike, and the answer to a known spike is pre-scaling.
Part 2 — CI/CD for ML
ML CI/CD Pipeline
Standard software CI/CD (test → build → deploy) extended to handle data, models, and experiments — not just code.
ML CI/CD pipeline: code commit triggers data validation → training → evaluation → registry → serving
  • GitHub Actions / Jenkins: trigger training jobs on push to main or on schedule
  • Data validation gate: Great Expectations / Pydantic schema checks before training; fail fast if distribution shifts
  • Automated evaluation gate: new model must beat champion on held-out set — else fail the pipeline
  • Model versioning: every training run tagged with git SHA, dataset hash, hyperparams
  • Rollback: re-promote previous model version in registry → redeploy — takes minutes
  • Smoke tests: integration tests on model endpoint (latency, output schema) before prod promotion
What makes this different from software CI is that the artifact is a function of data, so the same commit produces a different model tomorrow. That breaks the central assumption of ordinary CI — that green tests on a commit mean the build is good — and it is why the pipeline needs two gates a software pipeline does not have: a data gate before training, and a metric gate after it. Reproducibility therefore requires pinning three things, not one: the git SHA, the dataset version (a Delta version or snapshot hash), and the environment. Any of the three left floating and "why did last month's model behave differently" is unanswerable.
Design the evaluation gate carefully, because a naive one blocks every deployment. "Must beat the champion" on a noisy held-out set fails roughly half the time on a genuinely equal model — compare against a threshold that accounts for the metric's variance, and prefer a fixed, versioned evaluation set so that a moving benchmark is not confused with a moving model. Add non-negotiable checks that are not about the headline number: subgroup metrics must not regress, latency must stay inside budget, and the output schema must be unchanged. A model that lifts AUC by 0.002 while doubling P99 latency should fail the pipeline, and only an explicit gate will make it.
Finally, the retraining trigger in the diagram deserves a decision rather than a cron entry. Scheduled retraining is simple and retrains when nothing has changed; drift-triggered retraining is responsive and can chase noise into a retrain loop. The usual compromise is a schedule as a floor, drift as an interrupt, and the same evaluation gate on both paths so an automated retrain cannot ship a worse model unattended.
Part 3 — Cost Optimisation

Spot is close to free money for training and wrong for serving — an interrupted training job resumes from a checkpoint, an interrupted inference Pod drops live requests. The rule that makes spot usable is that checkpoint interval sets your worst-case loss: checkpoint every 20 minutes and an eviction costs at most 20 minutes of compute, so the interval is chosen against the eviction rate, not by habit.
Serving Cost Optimisation
TechniqueSavingsNotes
Request batching3–5× GPU throughputGroup requests; adds latency

Batching trades the latency of the first request for the throughput of all of them, which is the right trade under load and the wrong one when idle — so the batching window must be a timeout as well as a size, or a quiet period leaves a lone request waiting for companions that never arrive. And do the capacity arithmetic before optimising anything: at 8,000 QPS with a 40 ms service time you need 320 concurrent slots, and at a 70% utilisation target that is about 457 replicas. Halving the service time halves the fleet, which usually dwarfs any per-instance saving in the table above.
Part 4 — LLM Serving: vLLM & Triton
vLLM — PagedAttention
The bottleneck in LLM serving is the KV cache — it grows linearly with sequence length and batch size, causing memory fragmentation and low GPU utilisation.
  • PagedAttention: manages KV cache like OS virtual memory — allocates fixed-size "pages" on demand, no fragmentation
  • Continuous batching: new requests slot in as sequences finish — no waiting for entire batch to complete; 23× higher throughput vs naive batching
  • Tensor parallelism: splits model weights across multiple GPUs (needed for 70B+ models)
  • Speculative decoding: small draft model proposes tokens; vLLM verifies in parallel; 2–3× faster for high-latency models
  • OpenAI-compatible API — drop-in replacement for OpenAI endpoints
NVIDIA Triton Inference Server
NVIDIA's multi-framework serving platform — supports PyTorch, TensorFlow, ONNX, TensorRT in a single server.
  • Ensemble models: chain preprocessing → model → postprocessing in a single inference request
  • Dynamic batching: accumulates requests and batches before forwarding to model
  • TensorRT backend: JIT compiles PyTorch/ONNX to TensorRT → 3–5× faster GPU inference
  • Model repository: hot-reloading — deploy new model version without server restart
  • GRPC + HTTP: supports both protocols; GRPC preferred for high-throughput production
  • Best for: classical ML serving pipelines, multi-model ensembles, non-LLM deep learning
Worked — the memory budget for a 70B model, and why the KV cache is the problem
Almost every LLM serving decision falls out of one arithmetic exercise. Take a 70B-parameter model on an 80 GB A100.
WhatSizeConsequence
Weights, FP16 (2 bytes/param)140 GBDoes not fit. Needs tensor parallelism across 2+ GPUs
Weights, INT870 GBFits, with 10 GB left for everything else — too tight
Weights, INT4 / AWQ35 GBFits comfortably on one card
KV cache per token (80 layers, 8 KV heads, head-dim 128, FP16)0.33 MB—
KV cache, one 4,096-token sequence1.34 GB—
KV cache, 32 concurrent 4k sequences43 GBLarger than the quantised weights
Read the last two rows together: 35 GB of INT4 weights plus 43 GB of KV cache is 78 GB on an 80 GB card. The weights are the fixed cost and the KV cache is the variable one, so concurrency — not model size — is what actually exhausts the GPU. That single fact explains the whole design of vLLM. Classic serving pre-allocated a contiguous KV region per sequence sized for the maximum length, so a request that generated 200 tokens still reserved 4,096 tokens' worth; PagedAttention allocates fixed-size pages on demand instead, and the memory you stop wasting becomes extra concurrent sequences, which is where the throughput gain comes from.
It also explains grouped-query attention. With full multi-head attention at 64 KV heads the same model would need 2.62 MB per token — 8× more — putting 32 concurrent 4k sequences at over 340 GB. GQA is not a minor efficiency tweak; it is what makes long-context serving affordable at all. And it explains why continuous batching matters more than bigger batches: sequences finish at different times, so a static batch holds memory hostage to its slowest member, while slotting new requests into freed pages keeps utilisation high.

📖 Profiling tip

Profile P99 latency, not P50. P50 hides tail latency spikes that users actually experience. For ML pipelines, the database / feature store lookup is often the bottleneck — not the model itself.

Percentiles do not add, and this is the arithmetic that surprises people. If one request depends on several backend calls and each is slow 1% of the time, the chance that at least one is slow compounds:
Sequential calls per request151050100
P(at least one hits its own P99)1.0%4.9%9.6%39.5%63.4%
So a service that fans out to ten dependencies each with a perfectly respectable 1-in-100 slow tail is slow on roughly one request in ten — its P90, not its P99, is set by its dependencies' P99. This is Dean and Barroso's "tail at scale", and it has two practical consequences for ML serving. Reducing the number of sequential hops beats optimising any one of them — batch the feature lookups into a single multi-get rather than a loop of gets, which is the single most common fix. And a fallback path is a latency feature, not just an availability feature: a hedged request or a timeout that returns a default feature value converts a long tail into a slightly worse prediction, which is almost always the better trade.
Two more habits worth keeping. Measure at the client, because server-side timers exclude queueing, connection setup and serialisation — the parts that actually degrade under load. And watch the utilisation cliff: queueing delay rises non-linearly as a server approaches saturation, so the same system that is comfortable at 70% utilisation is unusable at 90%, which is why the capacity arithmetic above targets 70% rather than 95%.
Part 5 — Drift Detection & Monitoring
Drift Types & Detection
TypeWhat ChangesDetection Method
Data driftP(X) — input distribution shiftsPSI, KS test, MMD per feature
Concept driftP(y|X) — relationship changesMonitor performance metrics over time
Label driftP(y) — outcome prevalence changesMonitor positive rate; alert on deviation
Prediction driftP(ŷ) — model output distribution shiftsPSI on score distribution
Label delay is what forces this hierarchy. Concept drift is the one that actually matters and it is only measurable once labels mature — if a default takes 90 days to confirm, performance monitoring is a 90-day-lagging indicator. Data and prediction drift need no labels and are available today, so they are the early warning; performance is the confirmation that arrives a quarter late. Prediction drift is the most useful single monitor for the money it costs: the score distribution aggregates every input feature, so a shift in it catches upstream breakage that a per-feature check might spread too thin to flag.
A/B & Deployment Strategies
  • Shadow mode: new model runs alongside old, predictions logged but not acted on — zero business risk, no business metric feedback
  • Canary release: route 5–10% of traffic to new model; monitor; scale up if healthy
  • Champion-challenger: champion = current production; challenger = new model; compare on live traffic
  • Multi-armed bandit: dynamically allocate traffic to better variant; faster than fixed A/B but harder to interpret for statistical significance
They answer different questions and belong in sequence. Shadow mode validates the plumbing — latency, schema, null rates, and whether the online features match the offline ones — and it cannot tell you anything about business impact, because nothing acts on the predictions. Canary validates the impact on a small blast radius. Run shadow first; a model that disagrees wildly with the champion in shadow has a feature bug, not an insight.
A caution on canaries: a 5% canary is usually underpowered for the business metric you care about. It is sized to bound damage, not to measure a small lift, so treat "no significant difference at 5%" as "nothing exploded" rather than as evidence the model is equivalent — and see the causal-inference topic for the sample size an actual comparison needs.
Worked — a drift alarm that fires before any label arrives
The code card at the end runs a two-sample KS test between the training distribution of a feature and a live sample. Training draws utilisation from Beta(2, 5); the live traffic is Beta(2.6, 5) — a shift small enough to be invisible on a dashboard sparkline.
QuantityValueReading
Training mean utilisation0.286the distribution the model learned
Live mean utilisation0.349a 6-point shift — plausible as a real population change
KS statistic0.164max gap between the two CDFs
p-value< 1e-6alert fires
The trap in that p-value is sample size. With 10,000 training rows against 3,000 live rows, KS will flag differences far too small to affect any prediction — and at production volumes it flags essentially everything, every day. That is how drift monitoring gets muted and then ignored. Alert on effect size, not significance: use the KS statistic itself, or PSI with its conventional bands (below 0.10 stable, 0.10–0.25 investigate, above 0.25 act), and set the threshold from what actually moves your metric. A drift alarm nobody acts on is worse than none, because it consumes the attention the real one will need.

Adopt these in the order the pain arrives, not top to bottom. Experiment tracking and a model registry pay for themselves on day one, because without them you cannot say which artifact is in production or what produced it. A feature store is the expensive one and is only worth it when features are genuinely shared across teams or when you need online serving — for a single team with one model it is infrastructure standing in for a convention. The honest failure mode of this table is a platform team building all seven layers for three models.
Feature Store — Why It Matters
  • Training-serving skew: features computed differently in batch (training) vs real-time (serving) → model sees different distributions at inference time — feature store enforces the same transformation logic everywhere
  • Point-in-time correct joins: when training, join only features available AT the prediction time — prevents future leakage
  • Reuse across teams: "customer_30day_payment_rate" computed once, used by fraud, collections, and marketing models
  • Offline store (S3/DeltaLake) for training; online store (Redis) for <5ms serving latency
The value is the single feature definition, not the Redis cache — and it only materialises if you use the point-in-time API for training data. A team that adopts a feature store and then builds its training set with a hand-written latest-value join has bought the infrastructure and kept the bug. See the data-engineering topic for the three-row example of exactly that join going wrong.
Mistakes that survive code review
  • Two implementations of one feature. Batch pandas for training, real-time SQL or Redis for serving. They diverge on the untested cases and the model degrades with no error anywhere. One definition, both paths
  • Pinning the code and not the data. Reproducibility needs git SHA and dataset version and environment. Any one floating makes "why did last month's model differ" unanswerable
  • Unpinned dependency ranges in the image. A container built from loose requirements is a different container next month — the exact problem containers were adopted to solve. Lockfile, and pin the base image by digest
  • A liveness probe shorter than model load time. Kubernetes kills the Pod mid-load, restarts it, and the deployment never converges. Use a startup probe
  • Autoscaling GPU inference on CPU utilisation. The GPU saturates at 30% CPU, the HPA never fires, latency doubles. Scale on QPS, queue depth or GPU metrics — and pre-scale for known spikes, since a new Pod needs minutes to load weights
  • Assuming percentiles add. Ten dependencies at 1% slow each means about 10% of requests are slow. Cut hops — one multi-get instead of a loop — before optimising any single call
  • Drift alerts wired to p-values. At production volumes every feature is significantly different every day. Alert on effect size — KS statistic or PSI bands — or the alarm gets muted
  • Waiting for performance metrics to detect breakage. With a 90-day label delay that is a 90-day-lagging indicator. Prediction drift is available today and catches most upstream failures
  • An evaluation gate that only checks the headline metric. A model that adds 0.002 AUC, doubles P99 and regresses a subgroup should fail. Gate on latency, schema and subgroup metrics too
  • Reading a 5% canary as proof of equivalence. It bounds damage; it is not powered to measure a small lift
  • Spot instances for real-time serving. Fine for training, where a checkpoint resumes; an evicted inference Pod drops live requests
  • A rollback that has never been executed. Keep the previous version warm and switchable by config rather than redeploy, and rehearse it. An untested rollback is a plan, not a capability
  • No fallback when a feature is missing. A null reaching the model produces a confident nonsense score. Decide the default per feature, and count how often it is used

🎯 In an interview

Open with why ML deployment is not ordinary deployment. "A model is a function of data as well as code, so it can break while every test passes and every service is green — the failure mode is silence. That is why the pipeline needs two gates software CI does not have: a data gate before training and a metric gate after it, and why reproducibility means pinning three things — git SHA, dataset version, environment."

Name training–serving skew as the top failure and say what actually fixes it. "Training computes a feature in Spark with a left join so missing customers get NULL; the service recomputes it in Python with an inner join and returns 0.0. Nothing errors. The fix is a single feature definition used by both paths — and the feature store only delivers that if the training set is built with its point-in-time API, not a hand-written latest-value join."

Have the tail-at-scale number. "Percentiles do not add. Ten sequential dependencies each slow 1% of the time make about 10% of requests slow — the service's P90 is set by its dependencies' P99. So reduce hops before optimising any single call: one batched multi-get instead of a loop, and a timeout with a default feature value, which converts a long tail into a slightly worse prediction."

For the 70B serving follow-up, do the memory arithmetic out loud. "FP16 weights are 140 GB, so it does not fit on an 80 GB A100 — either tensor-parallel across two cards or quantise to INT4 at 35 GB. But the interesting part is the KV cache: with GQA it is about 0.33 MB per token, so 32 concurrent 4k sequences is 43 GB — larger than the quantised weights. Concurrency exhausts the GPU, not model size. That is what PagedAttention addresses: no per-sequence over-allocation, and the reclaimed memory becomes more concurrent sequences. Without GQA the same cache would be 8× bigger."

What not to say. Do not say "MLOps is deploying the model" — the loop is monitor, detect drift, retrain, gate, canary, monitor. Do not propose real-time serving by default; batch is the correct default and real-time is an escalation when someone is blocked on the answer. Do not claim a feature store prevents leakage on its own. Do not alert on drift p-values at production volume. And do not describe a rollback you have not rehearsed — if it requires a redeploy and a code change, it is not a rollback.

# 2. CONTRACT AT THE EDGE. Reject bad input at the boundary with a clear error,
#    rather than silently scoring a null and returning a confident number.
class ScoreRequest(BaseModel):
    user_id: int
    utilisation: float = Field(ge=0, le=1)
    n_accounts: int = Field(ge=0, le=100)

# 3. DRIFT: compare live features against the training distribution, per feature.
def drift_report(train: pd.DataFrame, live: pd.DataFrame, alpha=0.01):
    out = {}
    for c in train.columns:
        stat, p = ks_2samp(train[c], live[c])
        out[c] = {'ks': round(stat, 4), 'p': round(p, 6), 'alert': bool(p < alpha)}
    return out

rng = np.random.default_rng(0)
train = pd.DataFrame({'utilisation': rng.beta(2, 5, 10_000)})
live  = pd.DataFrame({'utilisation': rng.beta(2.6, 5, 3_000)})     # shifted
print(drift_report(train, live))
