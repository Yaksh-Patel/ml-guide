Model Cheatsheet
A reference, but not a lookup table — the useful version of this page is a decision procedure. Nearly every real choice is settled by four things you know before you fit anything: the shape of the data, how much of it there is, whether a person has to be told why, and how fast the answer must come back. Read each table below as "what the constraint forces", not "what is best", because outside a benchmark there is no best — there is only what survives your constraints and what you can defend when it fails.

For tabular data the honest default is gradient boosting, and it is not close. Deep learning has repeatedly failed to displace it on heterogeneous tabular problems, and the reasons are structural rather than a matter of tuning effort: trees are invariant to monotone feature transforms so scaling and skew do not matter, they handle mixed types and missing values natively, and axis-aligned splits suit data whose columns mean unrelated things. A neural network has to learn all of that from data you probably do not have. Start with a GBM, and treat a neural network on tabular data as a claim requiring evidence.
Two rows carry warnings worth internalising. "No extrapolation" for tree models is not a footnote — a tree predicts a constant outside the range of its training data, so a boosted model asked about a value larger than anything it has seen returns the edge value forever. For a trending time series that is silently, systematically wrong, which is why the time-series topic reaches for a linear component. And KNN and DBSCAN both fail in high dimensions for the same reason: distances concentrate, so nearest and farthest neighbours become indistinguishable and "nearby" stops meaning anything. Reduce dimensions first or use a method that does not depend on a distance.

The loss is where you state what an error costs, so choose it from the cost and not from the task name. The regression rows are the clearest case: MSE squares the error, so one point ten times further away contributes a hundred times the gradient and the fit bends towards it — which is correct when large errors really are disproportionately bad, and wrong when large errors are usually bad data. MAE ignores the magnitude and is robust but has a constant gradient that makes optimisation sluggish near the optimum; Huber is quadratic near zero and linear in the tails, which is why it is the usual compromise. Note also what each one predicts: minimising MSE gives you the conditional mean, minimising MAE gives the conditional median, and on a skewed target those are different numbers and only one of them is the answer to your question.
On the imbalanced row: focal loss down-weights examples the model already gets right so the gradient concentrates on hard ones, which helps when the negatives are overwhelming and easy. But it changes the implied base rate, so the output is no longer calibrated — fine when you only need a ranking, disqualifying when the probability gets multiplied by money, as in the credit-risk topic. If the decision needs a real probability, train with plain cross-entropy, fix the operating point with the threshold, and calibrate afterwards.

Read the learning curve, not just the final gap — it answers the question the table cannot. Plot both errors against training-set size: if the validation curve is still falling at full data, more data will help; if the two curves have flattened and converged at a high value, more data is wasted money and the model is too simple. That single plot separates "collect more" from "build better", which is usually the most expensive decision on the project.
The fourth row is the one people misread. Excellent validation and poor test almost never means bad luck; it means the validation set stopped being held out. Either the split leaks — a group split by row rather than by customer, a shuffled split on time-ordered data — or you have tuned against validation so many times that it has become part of the training signal. That is why a genuinely untouched test set, opened once, is worth the data it costs.

Simpler modelVarianceHigh overfitting
L1 selects because its constraint region has corners on the axes, so the optimum tends to land where a coefficient is exactly zero; L2's region is round and has no corners, so coefficients shrink towards zero without reaching it. That geometry is the entire difference and it decides which to reach for: L1 when you believe most features are irrelevant and want the model to say which, L2 when you believe many features each carry a little signal. With correlated features L1 arbitrarily keeps one of a group and drops the rest, which is why elastic net exists.
"More data" is listed as always best and deserves its caveat: it only fixes variance. If the curves have already converged, more rows change nothing — and more informative rows are not the same as more rows, which is why a small deliberately-collected sample from the region your model is worst in often beats another million from the same distribution.
Data Problem Diagnostic Checklist
  • ✅ Class imbalance? → PR-AUC metric, class weights or SMOTE, threshold tuning
  • ✅ High cardinality categoricals? → target encoding with CV, embeddings, count encoding
  • ✅ Missing data? → add missingness indicator + impute; XGBoost handles NaN natively
  • ✅ Multicollinearity? → check VIF, use Ridge or PCA before linear models
  • ✅ Outliers? → Huber loss for regression; robust scalers; Winsorize at 1st/99th percentile
  • ✅ Data leakage? → features collected after prediction time; always check temporal ordering
  • ✅ Label noise? → label smoothing, robust loss functions, confidence learning (cleanlab)
  • ✅ Distribution shift at serving? → PSI monitoring, trigger retraining when PSI > 0.1
Only one item on that list can invalidate everything above it, and it is leakage. The others cost you accuracy; leakage costs you the ability to know your accuracy, so run it first — and note that both supervised encodings in the list, target encoding and SMOTE, are themselves leakage risks unless they are fitted inside the cross-validation loop. See the Python/SQL/DSA topic for the run where an out-of-loop selection step scored 0.892 AUC on pure noise.
Two entries worth a sharper reading. Missingness is usually informative — a blank income field on an application often predicts the outcome better than any value would — so the indicator column matters more than the imputation method, and imputing without it destroys signal. And multicollinearity harms coefficients, not predictions: a collinear model still predicts fine and its individual coefficients become unstable and uninterpretable, so it is a problem exactly when you intend to read the coefficients, and largely irrelevant for a boosted model you were only ever going to interpret with SHAP.
Mistakes that survive code review
  • Skipping the baseline. Majority class, or the current rule engine. Without it you cannot tell whether 0.83 AUC is good, and the answer is embarrassingly often "no"
  • Reaching for a neural network on tabular data. Gradient boosting still wins there for structural reasons — monotone invariance, mixed types, native missing handling. Make the NN earn its place against a tuned GBM
  • Extrapolating with a tree model. It predicts a constant beyond the training range. On a trending target that is systematically wrong and no amount of tuning fixes it
  • Distance-based methods in high dimensions. KNN and DBSCAN both degrade as distances concentrate; reduce dimensions first or choose a different family
  • Choosing the loss from the task name. MSE gives the conditional mean, MAE the median — on a skewed target only one answers your question
  • Focal loss or SMOTE where the probability is used as a probability. Both change the implied base rate, so the output is no longer calibrated. Fine for ranking, disqualifying for pricing or provisioning
  • Target encoding or resampling fitted outside the CV loop. Both are supervised, so both leak. Inside the pipeline, always
  • Imputing without a missingness indicator. The fact that a field was blank is frequently the strongest feature in the row
  • Treating multicollinearity as a prediction problem. It destabilises coefficients. If you are reading SHAP off a GBM, it mostly does not matter
  • Tuning against the test set by repetition. Fifty peeks at the held-out set makes it a training set. Keep one split genuinely untouched and open it once
  • Answering "more data" without checking the learning curve. If the curves have converged, more rows buy nothing and the model is too simple
🎯 In an interview

Answer "which model would you use" with the constraints, not a name. "It depends on four things I'd want to know first: the shape of the data, how much there is, whether the decision has to be explained to anyone, and the latency budget. For tabular data with enough rows and no explanation requirement, gradient boosting is the default and I'd need a reason to deviate. If it has to be defended to a regulator, a scorecard or a GBM with monotone constraints and SHAP. Under a few thousand rows, a regularised linear model — a GBM will overfit."

Justify the tabular default structurally. "Trees are invariant to monotone transforms, so scaling and skew don't matter; they take mixed types and missing values natively; and axis-aligned splits fit data whose columns mean unrelated things. A neural network has to learn all of that from data you usually don't have. That's why deep learning hasn't displaced boosting on tabular problems despite a lot of effort."

Diagnose from the learning curve. "Train error high and validation high is bias — more capacity. Train low and validation high is variance — more data or more regularisation. But I'd plot both against training-set size before recommending 'collect more data': if the curves have flattened and converged, more rows change nothing and the model is too simple. That plot decides the most expensive question on the project."

Have the L1/L2 geometry ready. "L1's constraint region has corners on the axes, so the optimum tends to land with coefficients exactly zero — that's why it selects. L2's region is round, so coefficients shrink without reaching zero. L1 when I think most features are irrelevant; L2 when many carry a little signal; elastic net when features are correlated, because L1 keeps one of a correlated group arbitrarily."

What not to say. Do not name a model before asking about constraints. Do not offer "I'd try a neural network" for tabular data without a baseline. Do not say "more data always helps" — it only fixes variance. Do not describe SMOTE or focal loss as free wins; they change the base rate and break calibration. And do not quote a metric without a baseline next to it, because 0.83 AUC is meaningless until you know what the majority-class rule scores.
